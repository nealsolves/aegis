# AEGIS Demo Site Redesign

**Date:** 2026-07-25

**Status:** Approved design

**Public frontend:** GitHub Pages at `https://nealsolves.github.io/aegis/`

**Demo backend:** Render at `https://aegis-demo-api.onrender.com`

## 1. Purpose

The current demo begins with SDK architecture and assumes that the visitor
already understands AI governance. The redesigned site must first explain the
problem in plain language, then let visitors see AEGIS make decisions, and
finally expose the SDK details needed by developers.

The site serves a wide audience:

- people using AI who have heard about governance but do not yet know what it
  changes;
- technical executives deciding whether model logs or thought traces are
  sufficient;
- developers comparing AEGIS with provider platforms such as Amazon Bedrock
  AgentCore;
- governance, risk, audit, and compliance staff who need evidence rather than
  model explanations;
- SDK evaluators who want exact integration patterns and testable behavior.

The design uses a separate introduction page and demo area:

1. The introduction explains what AEGIS does, where it sits, why thought traces
   are insufficient, and how to install it.
2. The demo contains Architecture, Scenarios, Labs, and FAQ.
3. Render supplies deterministic model and adapter fixtures and executes the
   real AEGIS SDK.

## 2. Product statement

The central public explanation is:

> AEGIS checks an AI call before it runs and checks the result before your
> application uses it. Your policy decides who may act, which tools are
> allowed, what output is acceptable, and when a person must approve.

Agentic workflow support must be stated near the top of the introduction:

> AEGIS governs participants, step order, handoffs, approvals, budgets, and
> session lifecycle. Your application or agent framework still executes the
> agents, model calls, and tools.

The ownership boundary is:

- the host application executes;
- AEGIS checks and controls;
- separate evidence records what happened.

AEGIS governs both individual invocations and multi-step agentic workflows. It
does not become an agent runtime, scheduler, provider client, tool executor, or
credential store.

## 3. Thought traces and governance records

The introduction must distinguish model-generated reasoning from external
governance without dismissing the diagnostic value of thought traces.

### Model thought trace

- generated by the model being inspected;
- useful for debugging and behavioral inspection;
- may omit an influence or produce a plausible account after the fact;
- cannot independently stop an unauthorized action before execution;
- does not prove which company policy was applied.

### AEGIS governance record

- generated outside the model;
- tied to a versioned policy and ordered checks;
- may stop a request before the model or tool runs;
- may reject output before the host application uses it;
- records the decision, reason codes, checksums, policy metadata, and workflow
  context.

The page should cite primary research or vendor research when making
faithfulness claims. The public copy must avoid claiming that every thought
trace is false or useless.

### 5.4 Installation and first integration

The page presents four steps:

1. Install `aegis-ai-governance==0.9.0b1`.
2. Choose a supplied policy profile or YAML policy.
3. Run split enforcement around the host call.
4. Store the returned artifact through a supported sink.

The first code sample uses the public split API:

```python
from aegis import enforce_post_call, enforce_pre_call

pre = enforce_pre_call(
    {
        "policy_file": "policies/support.yaml",
        "model_provider": "anthropic",
        "model_identifier": "claude-sonnet-4-6",
        "role": "support_agent",
        "input": {"query": customer_message},
        "context": {"customer_verified": True},
    }
)

reply = model.generate(customer_message)
artifact = enforce_post_call(pre, {"result": reply})
```

The final implementation must verify the example against the public API and the
selected sample policy.

## 6. Architecture area

### 6.1 Progressive detail

The Architecture page has two views:

- **Technical map** contains SDK entry points, workflow governance,
  invocation-gate order, adapters, evidence, and operator tooling.

The default view has three zones:

1. Host executes.
2. AEGIS governs.
3. Evidence records.

workflow step.

### 6.2 Diagram connection rules

Every connector must follow these rules:

- use dedicated empty space between nodes;
- use short horizontal connections on wide layouts;
- use separately constructed short vertical connections on narrow layouts;
- never rotate a long horizontal connector to simulate a vertical path;
- enter and exit at named edge ports;
- stop at the node boundary;
- place connector labels above a horizontal line or beside a vertical line;
- keep labels on opaque backgrounds;
- never cross a node, text label, boundary, or another connector;
- use one dominant direction of travel in each map;
- render component relationships and enforcement sequence as separate maps.

Text inside a node must have fixed padding and a wrapping limit. Long technical
notes belong in a detail panel, not inside the diagram.

### 6.3 Interaction and accessibility

The default **How it works** diagram is semantic React markup and CSS, not a
single image. Nodes, connector lanes, labels, and detail panels remain separate
elements so the layout can change cleanly by breakpoint.

The desktop **Technical map** may continue to use generated SVG assets, but
those assets must come from one maintained diagram source and the existing
rendering script. Light and dark variants are generated from that source; they
are not adjusted as independent handwritten copies. The phone layout uses
semantic grouped cards instead of scaling the desktop SVG.

Selecting a node opens a concise explanation of:

- what the component does;
- who owns it;
- which public API or artifact represents it;
- what AEGIS does not own.

On a phone, zones stack and connectors occupy dedicated rows between them. The
technical map becomes grouped cards instead of shrinking into unreadable text.
Every diagram has a plain-text summary for screen readers.

## 7. Roleplay scenarios

### 7.1 Shared interaction pattern

Every scenario uses the same sequence:

1. Introduce the people, system role, policy, and incident.
2. Show the deterministic model response supplied by Render.
3. Ask the visitor to choose what should happen.
4. Run the real AEGIS evaluation.
5. Show each gate, decision, reason code, and artifact.
6. Correct the input, policy source, role, or workflow and replay.

The visitor choice creates engagement but does not change or manufacture the
AEGIS result. The backend result is authoritative.

### 7.2 Atlas Travel

**Visitor role:** customer-support supervisor.

**Incident:** a fictional airline assistant promises that a bereavement
discount can be applied after travel. The response has no policy citation and
matches the failure pattern in *Moffatt v. Air Canada*, 2024 BCCRT 149.

**First run:**

- role and basic support context pass;
- the model output is supplied by a deterministic Render fixture;
- `ProvenanceGate` finds no source IDs;
- the required `policy_citation` is missing;
- the refund commitment lacks required approval;
- AEGIS blocks the reply and emits a failure artifact.

**Correction:**

- the agent calls the policy lookup tool;
- the response cites fictional policy section `BRV-04`;
- the answer states the actual application condition;
- a human handoff is offered;
- the corrected run passes and emits a signed invocation artifact.

**Primary features:** output schema, postconditions, provenance, human handoff,
tool budget, signing, reason codes, and post-call enforcement.

### 7.3 Northstar Health

**Visitor role:** clinic operations lead.

All people and records are fictional. The fixture must not contain real patient
data or medical advice.

**First act:**

- a scheduling assistant requests restricted patient history;
- the assistant role is not authorized for the requested data;
- Phase A stops the call before model use;
- the artifact records the role and precondition failure.

**Authorized retry:**

- an authorized nurse requests a limited summary;
- the deterministic response includes an unsupported treatment recommendation;
- privacy and clinical-scope custom gates reject the recommendation;
- risk scoring is not reached because the custom gate has already stopped the
  pipeline;
- the output is held at a physician approval checkpoint;
- the public response may call the observed state `PAUSED`, while the authentic
  finalized workflow artifact remains `INCOMPLETE` with the pending checkpoint.

**Primary features:** role authorization, typed preconditions, split
enforcement, custom gates, strict risk treatment, risk evidence, policy
composition, and approval checkpoints.

### 7.4 Meridian Finance

**Visitor role:** finance operations manager.

All invoices, vendors, amounts, accounts, and identities are fictional. The
demo does not transmit a payment.

**Workflow:**

1. invoice intake;
2. vendor verification;
3. risk review;
4. payment preparation;
5. approval.

**Fault:**

- the payment participant attempts to skip vendor verification;
- it tries an unauthorized transition and payment-tool call;
- AEGIS rejects the transition, records the participant, applies the tool
  budget, and pauses at the approval checkpoint.

**Correction:**

- the required sequence is followed;
- the authorized participant performs each step;
- the approval is recorded;
- the session completes;
- trace links invocation artifacts to the separate workflow artifact;
- export packages the evidence.

**Primary features:** `GovernanceSession`, participants, roles, required
sequence, allowed transitions, handoffs, budgets, approval, lifecycle,
invocation/workflow evidence separation, trace, and export.

### 7.5 Scenario authenticity

The browser may contain descriptive case metadata and visitor-interface copy.
It must not contain the authoritative model outcome, AEGIS status, score,
reason codes, or artifact.

Render owns:

- deterministic model-response fixtures;
- provider-native adapter fixtures;
- policy references;
- fixture versions;
- the actual AEGIS call;
- the response containing transcript, decision, and artifacts.

If Render or AEGIS fails, the UI reports that the governance run did not
complete. It must not substitute a successful static fixture.

### 10.3 Bedrock and AgentCore wording

The FAQ must state that AEGIS does not replace AgentCore.

AgentCore responsibilities named in the comparison may include:

- managed agent runtime and deployment;
- identity, memory, gateway, and observability services;
- browser and code-execution tools;
- Cedar policies associated with Gateway tool calls.

AEGIS responsibilities named in the comparison may include:

- pre-call and post-call policy checks in host code;
- roles, input rules, output rules, and risk treatment;
- workflow participants, sequence, handoffs, approvals, budgets, and
  lifecycle;
- portable invocation and workflow evidence tied to the AEGIS policy.

The comparison describes product boundaries. It does not claim that every
AgentCore execution path has been tested with the current Bedrock adapter.

The Bedrock adapter subsection must state:

- the host supplies Bedrock request and response evidence;
- the adapter converts supported evidence into the shape AEGIS evaluates;
- the adapter does not create the Bedrock client;
- the adapter does not hold AWS credentials;
- the adapter does not invoke a model, deploy an agent, own transport, or own
  retries;
- compatibility claims require the separate Bedrock adapter validation task.

### 12.3 Public API contract

The redesign adds:

#### `GET /api/demo/manifest`

Returns:

- API contract version;
- AEGIS SDK version;
- fixture-set version;
- backend branch and commit;
- available scenarios;
- available deterministic adapters.

#### `POST /api/demo/scenarios/{scenario_id}/runs`

Accepts a server-defined scenario variant such as `first_attempt` or
`corrected`.

Returns:

- scenario and fixture version;
- deterministic transcript;
- AEGIS invocation artifact;
- workflow artifact when applicable;
- structured error when enforcement fails before an artifact is available;
- backend and SDK provenance.

#### `POST /api/demo/adapters/{adapter_id}/runs`

Accepts a named deterministic adapter fixture.

Returns:

- provider-native input;
- normalized AEGIS evidence;
- decision;
- artifact;
- adapter and SDK provenance.

#### `GET /health`

Continues to return service readiness and Render deployment provenance.

Unknown scenario, variant, and adapter IDs are rejected. The API never accepts
an arbitrary fixture or policy path.

## 13. Service states and errors

The frontend checks `/health` and `/api/demo/manifest` when the visitor enters
the demo.

### Starting

While a free Render service wakes, the UI shows:

> Starting the demo API. Render may need about a minute after a period of
> inactivity.

Run controls remain disabled until the service is ready. The health check uses
a bounded retry period and exposes a manual retry when it expires.

### Unavailable

The UI names the failed operation, reports that the governance run did not
complete, and provides Retry. It does not display static success data.

### API contract mismatch

Scenario and lab run controls are disabled. The UI shows the frontend and
backend contract versions.

### Deployment commit difference

GitHub Pages and Render may deploy the same `main` commit at different times. A
commit difference is visible as provenance but is not an automatic failure.
The API contract version determines compatibility.

### AEGIS failure

When AEGIS attaches an audit artifact to an error, the API returns the artifact
and the structured error. The UI distinguishes an AEGIS policy decision from a
network or server failure.

### Stale request

Starting a new run aborts or supersedes the previous request. An older response
must not replace a newer result.

## 14. Security and privacy

- No BYOK fields appear in the public site.
- No provider credentials are stored in the frontend or sent to Render.
- All people, medical records, invoices, accounts, vendors, and company names
  in the scenarios are fictional.
- No scenario transmits a payment or requests real medical advice.
- Scenario, variant, and adapter inputs use server-side enums.
- Request bodies and downloadable artifacts are bounded and validated.
- CORS uses an allowlist.
- Downloaded artifact JSON is built from the current API response.
- The site must not imply that AEGIS replaces provider, runtime, network,
  tenant-isolation, or secret-management controls.
