# `v0.9.0` PR-10d Detailed Design Spec - Research Safety Addendum

Date: 2026-05-03
Status: Proposed
Baseline: PR-09 on `develop`, with PR-10c local work expected before final
adapter-specific fixture gates
Target branch: `feat/v0.9-10d-research-safety-addendum`

---

## 1. Release Context

PR-10d is a bounded hardening addendum for the `v0.9.0` beta train. It adds
research-informed safety checks to existing AEGIS workflow governance surfaces:

- `aegis workflow lint`
- `aegis workflow doctor`
- `aegis workflow trace`
- `aegis workflow export`
- workflow starter safety tests
- optional adapter fixture tests when adapter surfaces have landed
- internal `ValidatorHook` examples

This design preserves the current ownership boundary:

- the host still owns orchestration, provider calls, tools, network transport,
  credentials, retries, and memory
- AEGIS still owns deterministic workflow governance, diagnostics, evidence,
  and fail-closed rejection behavior

PR-10d must not add a hosted runtime, workflow orchestrator, transport proxy,
MCP gateway, streaming runtime, memory manager, formal model checker, or
LLM-as-judge engine.

---

## 2. Review Summary Of The Plan

The PR-10d plan is implementable against the current source tree, but the code
implementation should respect these existing contracts:

- `workflow_lint.py` currently returns finding dicts with stable
  `code`, `message`, `target_kind`, and `path`.
- The CLI exits `1` for any lint finding and prints only `code` and `message`
  in human mode.
- `workflow_doctor.py` owns `severity` and `next_action`.
- `workflow_export.py` already preserves `steps[i].metadata` in operator mode
  and includes step metadata in audit summaries when present.
- `GovernanceSession.enforce_step_post_call(..., step_metadata=...)` is already
  the source artifact seam for adapter or host-supplied step metadata.
- The workflow policy schema already exposes the fields needed for static graph
  analysis: `required_sequence`, `allowed_transitions`, `participants`,
  `handoffs`, `max_steps`, `max_total_tool_calls`, `escalation`, and
  `protocol_constraints`.

The main design constraint is that PR-10d should add evidence and checks
additively. It should not replace existing reason codes where tests and docs
already rely on them, and it should not add remediation text to lint findings.

---

## 3. Goals

PR-10d should:

- add deterministic graph and topology lint over existing workflow policy DSL
  fields
- include bounded witness traces and structured evidence for new static lint
  findings
- keep doctor as the single owner of severity and next-action remediation
- add source and memory provenance warnings in doctor without blocking the
  default path
- project governance rationale metadata in workflow exports without breaking
  existing export consumers
- add focused safety smoke tests for starter workflows and workflow governance
  behavior
- add fixture-only adapter hardening tests for adapter surfaces that are present
  in the PR-10d target branch
- add an internal multi-aspect `ValidatorHook` example without public promotion

---

## 4. Non-Goals

PR-10d does not:

- introduce a temporal logic DSL
- infer sensitive semantics from arbitrary step names
- make `ValidatorHook` public
- add a new public workflow DSL field
- make adapter SDKs required dependencies
- import external benchmark suites
- persist raw provider payloads by default
- add network calls, credentials, or provider accounts to tests
- make `lint` warning-aware unless that is accepted as a separate CLI contract
  change

### 5.1 Lint

Primary file:

- `aegis/_internal/workflow_lint.py`

Current relevant behavior:

- `lint_policy(...)` validates YAML and schema first.
- If schema validation fails, semantic checks return early.
- Existing workflow checks include:
  - `WORKFLOW_STEP_BUDGET_EXCEEDED` when `required_sequence` length exceeds
    `max_steps`
  - `WORKFLOW_INVALID_TRANSITION` when transitions or handoffs reference

  - `WORKFLOW_UNSUPPORTED_BINDING` for unsupported protocol names
- `lint_starter_dir(...)` checks starter integrity and public import safety.
- `lint_workflow_artifact(...)` checks workflow artifact structure.

PR-10d should add graph helpers under policy lint after schema validation and

### 5.2 Doctor

- `aegis/_internal/workflow_doctor.py`

Current relevant behavior:

- `_NEXT_ACTIONS` maps stable codes to remediation strings.
- `_lint_to_doctor(...)` promotes every lint finding to `ERROR`.

codes. It should not add `next_action` to lint findings.

### 5.3 Export

Primary file:

## 6. Compatibility Rules

### 6.1 Lint Finding Shape

Extend `_finding(...)` additively:

```python
def _finding(
    code: str,
    message: str,
    target_kind: str,
    path: str,
    *,
    details: dict[str, Any] | None = None,
    witness_trace: list[dict[str, Any]] | None = None,
) -> dict:
    finding = {
        "code": code,
        "message": message,
        "target_kind": target_kind,
        "path": path,
    }
    if details:
        finding["details"] = details
    if witness_trace:
        finding["witness_trace"] = witness_trace
    return finding
```

Rules:

- Existing keys remain required.
- `details` and `witness_trace` are optional and JSON-serializable.
- Lint findings must not include `severity`.
- Lint findings must not include `next_action`.
- Human CLI output remains unchanged.
- JSON CLI output includes the new optional fields.

### 6.2 Witness Trace Bounds

Add a module constant:

```python
_MAX_WITNESS_TRACE_EVENTS = 8
```

Witness traces must be deterministic and bounded:

- no raw policy dump
- no unbounded path enumeration
- no recursion over arbitrary object depth
- sorted stable traversal when multiple next nodes are possible
- include a `"truncated": true` marker on the final event when capped

Recommended witness event shape:

```json
{
  "kind": "transition",
  "from_step": "collect",
  "to_step": "draft",
  "reason": "reachable"
}
```

### 6.3 Existing Codes

Do not replace existing codes in current checks:

- keep `WORKFLOW_STEP_BUDGET_EXCEEDED` for `required_sequence` length greater
  than `max_steps`
- keep `WORKFLOW_INVALID_TRANSITION` for references to undeclared steps or
  participants

New PR-10d codes are additive and should cover cases not already represented
by those checks.

```python
def _find_reachable_steps(
    start_step: str,
    transitions: dict[str, list[str]],

    ...

def _first_required_sequence_transition_conflict(
    required_sequence: list[str],
    transitions: dict[str, list[str]],
) -> dict[str, Any] | None:
    ...

    workflow: dict[str, Any],
) -> dict[str, Any] | None:
    ...
```

Call `_lint_workflow_graph(...)` from `lint_policy(...)` only after schema
validation and existing workflow reference checks.

### 7.2 Declared Step Universe

Use `workflow.required_sequence` as the authoritative declared step list.

Rules:

- If `required_sequence` is absent or empty, skip step reachability and dead-end
  checks.
- If `allowed_transitions` is absent or empty, skip transition-graph checks
  because runtime sequence enforcement can still govern the ordered sequence.
- Do not invent steps from arbitrary source code, comments, or names.
- Do not infer terminal/sensitive/external semantics from step names.

### 7.3 `WORKFLOW_UNREACHABLE_STEP`

Meaning:

- A declared step cannot be reached from the start step through
  `allowed_transitions`.

Trigger:

- `required_sequence` has at least one step.
- `allowed_transitions` is present.
- A declared step is not reachable from `required_sequence[0]`.

Message:

```text
workflow.required_sequence declares step '<step>' but it is not reachable from
the start step through workflow.allowed_transitions.
```

Details:

```json
{
  "declared_step": "review",
  "start_step": "collect",
  "known_predecessors": ["draft"],
  "reachable_steps": ["collect", "draft"]
}
```

Witness trace:

- bounded traversal events from the start step
- final blocked event:

```json
{
  "kind": "blocked_step",
  "step_id": "review",
  "reason": "not_reachable_from_start"
}
```

### 7.4 `WORKFLOW_DEAD_END_STEP`

Meaning:

- A non-terminal declared step has no valid next step under
  `allowed_transitions`.

Trigger:

- `required_sequence` is present.
- `allowed_transitions` is present.
- A step that is not the last required step has no valid declared successor in
  `allowed_transitions`.

Message:

```text
workflow.allowed_transitions gives non-terminal step '<step>' no valid next
step, so later required steps cannot run.
```

Details:

```json
{
  "step_id": "draft",
  "valid_next_steps": [],
  "remaining_required_steps": ["review", "publish"]
}
```

Witness trace:

```json
[
  {
    "kind": "dead_end",
    "step_id": "draft",
    "reason": "no_declared_successor"
  }
]
```

### 7.5 `WORKFLOW_REQUIRED_SEQUENCE_IMPOSSIBLE`

Meaning:

- `required_sequence` conflicts with transition rules and cannot complete.

Trigger:

- Consecutive required pair `(current_step, next_step)` exists.
- `allowed_transitions` is present.
- `next_step` is not in `allowed_transitions[current_step]`.

Message:

```text
workflow.required_sequence requires '<current>' before '<next>', but
workflow.allowed_transitions does not allow that transition.
```

Details:

```json
{
  "required_sequence": ["collect", "draft", "review"],
  "conflicting_rule": "allowed_transitions.collect",
  "from_step": "collect",
  "required_next_step": "draft",
  "allowed_next_steps": ["review"]
}
```

Witness trace:

```json
[
  {
    "kind": "required_pair",
    "from_step": "collect",
    "to_step": "draft",
    "reason": "required_sequence"
  },
  {
    "kind": "transition_missing",
    "from_step": "collect",
    "to_step": "draft",
    "reason": "not_allowed_by_allowed_transitions"
  }
]
```

Budget conflict rule:

- Keep the existing `WORKFLOW_STEP_BUDGET_EXCEEDED` finding when
  `len(required_sequence) > max_steps`.
- Enrich that existing finding with `details`:

```json
{
  "required_sequence_length": 4,
  "max_steps": 3,
  "conflicting_rule": "workflow.max_steps"
}
```

Do not emit an additional `WORKFLOW_REQUIRED_SEQUENCE_IMPOSSIBLE` for the same
budget conflict unless a separate transition conflict exists.

### 7.6 `WORKFLOW_UNBOUNDED_HANDOFF_LOOP`

Meaning:

- `workflow.handoffs` contains a participant cycle and the workflow has no
  static step budget or approval break.

Trigger:

- A directed cycle exists in `workflow.handoffs`.
- `workflow.max_steps` is absent.
- `workflow.escalation.require_approval_after_steps` is absent.
- `workflow.escalation.require_approval_for_roles` does not intersect roles of
  participants in the detected cycle.

Message:

```text
workflow.handoffs allows a participant cycle without max_steps or an approval
break.
```

Details:

```json
{
  "participants": ["researcher", "reviewer"],
  "cycle": ["researcher", "reviewer", "researcher"],
  "budget_rule": null,
  "approval_break": null
}
```

If `max_steps` is set, do not emit this finding. If
`require_approval_after_steps` is set, do not emit this finding. If
`require_approval_for_roles` intersects a role on the detected cycle, do not
emit this finding.

### 7.7 Duplicate Findings

Avoid noisy duplicates:

- Existing unknown-step `WORKFLOW_INVALID_TRANSITION` findings run first.
- If unknown-step findings exist, skip graph topology checks for
  `allowed_transitions` because the graph cannot be trusted.
- Emit at most one finding per new code per policy file in the first cut.
- Use deterministic first conflict selection based on `required_sequence` order
  and sorted participant IDs.

## 8. Workstream 2 - Temporal Checks Without A New DSL

### 8.1 Implementation Boundary

PR-10d must not infer temporal obligations from arbitrary step names. Temporal
checks may only run when the obligation is declared by one of these sources:

- generated starter profile metadata controlled by AEGIS
- adapter fixture metadata controlled by AEGIS tests
- explicit existing policy fields such as `required_sequence`,
  `allowed_transitions`, and `escalation`

### 8.2 Starter Metadata

Add internal starter profile metadata in `aegis/_internal/starter_templates.py`:

```python
_STARTER_SAFETY_METADATA: dict[str, dict[str, Any]] = {
    "standard": {
        "temporal_obligations": [
            {
                "code": "STARTER_APPROVAL_BEFORE_FINALIZATION",
                "before": "finalize",
                "requires": "approval_checkpoint",
            }
        ]
    },
    "regulated-high-assurance": {
        "temporal_obligations": [
            {
                "code": "STARTER_SOURCE_BEFORE_SUMMARY",
                "before": "summary",
                "requires": "source_bound_analysis",
            }
        ]
    },
}
```

This metadata is internal and test-facing. It is not a new public DSL.

### 8.3 Generated Starter Adjustments

To make starter safety checks deterministic, generated starters should use
explicit step IDs and step metadata:

```python
pre1 = session.enforce_step_pre_call(..., step_id="source_analysis")
session.enforce_step_post_call(
    pre1,
    output1,
    step_metadata={
        "governance": {
            "rationale": "source_bound_analysis",
            "decision_basis": ["provenance.source_ids"],
            "source_ids": ["doc-001", "doc-002"],
            "operator_action": "not_required",
            "waiver_id": None,
        }
    },
)
```

Rules:

- Keep starter examples public-import only.
- Keep examples runnable without external model APIs.
- Do not expose `_internal` imports in generated starter output.
- If policy `workflow.required_sequence` is added to a starter policy, the
  generated workflow example must pass matching explicit `step_id` values.

### 8.4 Temporal Check Placement

Do not add broad temporal lint over arbitrary starter code.

Instead:

- validate starter temporal expectations through focused smoke tests
- optionally add doctor INFO/WARNING guidance when exact generated profile
  metadata is identifiable
- avoid making starter temporal warnings lint blockers unless lint severity is
  separately introduced

Recommended first-cut doctor-only warning code:

- `WORKFLOW_STARTER_TEMPORAL_WARNING`

Doctor message example:

```text
The standard starter is expected to record an approval checkpoint before
finalization evidence. The generated example should preserve pause/resume before
post-approval steps.
```

## 9. Workstream 3 - Source And Memory Provenance Warnings

### 9.1 New Doctor Code

Add doctor-only code:

- `WORKFLOW_SOURCE_PROVENANCE_WARNING`

Default severity:

- `WARNING`

### 9.2 Trigger Sources

Implement in `workflow_doctor.py`, not `workflow_lint.py`.

Policy target:

- If a generated starter profile or exact `ProvenanceGate(require_source_ids=True)`
  pattern declares source-required behavior, doctor may emit an INFO/WARNING
  explaining required source IDs.
- Existing `WORKFLOW_SOURCE_REQUIRED` behavior remains for hard enforcement
  failures.

Workflow artifact target:

- Inspect `steps[i].metadata.governance`.
- If exact governance metadata declares source-bearing behavior, but no
  `source_ids`, emit `WORKFLOW_SOURCE_PROVENANCE_WARNING`. Acceptable exact
  markers are `decision_basis` entries such as `"provenance.source_ids"` or a
  boolean `source_required: true` under the governance object.
- If workflow metadata includes memory-like keys without source IDs, emit
  `WORKFLOW_SOURCE_PROVENANCE_WARNING`.

Audit artifact target:

- If `context` contains memory-like fields and neither
  `context.provenance.source_ids` nor top-level `provenance.source_ids` is
  present, emit `WORKFLOW_SOURCE_PROVENANCE_WARNING`.

Memory-like keys are exact-key checks only:

```python
_MEMORY_LIKE_KEYS = frozenset({
    "memory",
    "memories",
    "conversation_memory",
    "retrieved_memory",
    "retrieved_context",
    "knowledge_base_context",
})
```

Do not inspect arbitrary text values for semantic meaning.

### 9.3 Next Action

Add `_NEXT_ACTIONS["WORKFLOW_SOURCE_PROVENANCE_WARNING"]`:

```text
Attach context.provenance.source_ids or steps[i].metadata.governance.source_ids
for source-bearing context. If the step is intentionally non-evidence-bearing,
mark that in step metadata so operators can distinguish generated context from
source-backed evidence.
```

### 9.4 Blocking Behavior

This warning must not block:

- `workflow lint`
- default generated starter execution
- export generation
- base package smoke

Doctor human CLI exits `0` unless another `ERROR` finding exists.

## 10. Workstream 4 - Workflow Export Governance Rationale

### 10.1 Source Artifact Shape

The canonical source is:

```text
workflow_artifact.steps[i].metadata.governance
```

Expected keys:

```json
{
  "rationale": "approval_required_before_external_handoff",
  "decision_basis": ["allowed_transitions", "approval_checkpoint", "tool_budget"],
  "operator_action": "approval_granted",
  "approval_checkpoint_id": "checkpoint-123",
  "source_ids": ["doc-001"],
  "waiver_id": null
}
```

All keys are optional at runtime, but tests should cover the canonical full
shape.

### 10.2 Export Helper

Add helper in `workflow_export.py`:

```python
def _extract_governance_summary(step: dict[str, Any]) -> dict[str, Any] | None:
    metadata = step.get("metadata")
    if not isinstance(metadata, dict):
        return None
    governance = metadata.get("governance")
    if not isinstance(governance, dict):
        return None
    return _redact_governance(governance)
```

Add helper:

```python
def _redact_governance(governance: dict[str, Any]) -> dict[str, Any]:
    allowed = {
        "rationale",
        "decision_basis",
        "operator_action",
        "approval_checkpoint_id",
        "source_ids",
        "waiver_id",
    }
    ...
```

Rules:

- Keep only scalar values, null, and string arrays for canonical keys.
- Drop nested objects from governance summaries.
- Do not include raw provider prompts, tool inputs, trace payloads, or model
  outputs.
- Preserve operator mode's existing full step metadata pass-through.
- Add explicit `governance` summary in audit step summaries when present.

### 10.3 Operator Mode

Operator mode should remain backward-compatible by keeping existing `sessions`
shape.

Add a top-level optional summary under `integrity`:

```json
{
  "governance_rationale_count": 3
}
```

This count is additive and helps operators verify whether rationale metadata was
present without scanning every step.

Do not remove or reshape embedded invocation artifacts.

### 10.4 Audit Mode

Audit step summaries should add:

```json
{
  "governance": {
    "rationale": "approval_required_before_external_handoff",
    "decision_basis": ["allowed_transitions", "approval_checkpoint"],
    "operator_action": "approval_granted",
    "approval_checkpoint_id": "checkpoint-123",
    "source_ids": ["doc-001"],
    "waiver_id": null
  }
}
```

Rules:

- Continue copying `metadata` as currently done for compatibility.
- Add `governance` as a convenience projection, not a replacement for
  `metadata`.
- If governance metadata is malformed, omit the projection and let doctor warn
  in a future pass rather than failing export.

### 10.5 Export Tests

Add tests to `tests/test_workflow_export.py`:

- operator export preserves `steps[i].metadata.governance`
- operator integrity includes `governance_rationale_count`
- audit export projects redacted `steps[i].governance`
- audit export does not include unsupported nested governance payloads
- export works when governance metadata is absent
- export rationale appears for blocked, paused, failed, and completed fixture
  paths in the PR-10d smoke test file

## 11. Workstream 5 - Adapter-Informed Capability And Trust Tests

Adapter fixture tests are conditional on target-branch contents.

### 11.1 Sequencing Rule

At PR-10d implementation start:

- check whether PR-10a Bedrock adapter surfaces exist
- check whether PR-10b A2A adapter surfaces exist
- check whether PR-10c OpenAI Agents adapter surfaces exist

Only add fixture tests for surfaces present in the branch. Missing surfaces are
listed as deferred adapter-specific gates in docs and release gates.

### 11.2 Required Test Themes

For each present adapter surface, add fixture-only tests for:

- authoritative participant identity, not descriptive name matching
- capability mismatch fails closed
- protocol mismatch fails closed
- side-effecting or externalizing capability requires approval when policy
  already demands approval
- remote participant cannot widen role, protocol, capability, or handoff
  authority
- unsupported dynamic tool surfaces are explicitly rejected

### 11.3 OpenAI Agents Adapter Fixture Tests

If PR-10c surfaces are present, extend `tests/test_openai_agents_adapter.py` or
add `tests/test_pr10d_openai_agents_adapter_safety.py`.

Scenarios:

- wrapped function tool without authorization raises the adapter's fail-closed
  error
- `Agent.as_tool(...)` is treated as governed tool activity, not as a handoff
- observed handoff not declared at bind time fails closed
- hosted tools remain rejected when `allow_hosted_tools` is false
- trace-required protocol constraint fails when trace evidence is absent
- governance rationale metadata appears in step metadata after a governed run

No test may import the real provider runtime unless it is already optional and
skippable. Prefer fakes and simple fixture classes.

### 11.4 Bedrock And A2A Deferred Gates

If Bedrock or A2A source files are absent, add a deferred gate note rather than
a failing test:

```text
Deferred PR-10d adapter gate: Bedrock alias-backed participant identity tests
remain blocked until PR-10a surfaces are present.
```

Keep this note in:

- `RELEASE_GATES.md`
- `implementation_status.md`
- `docs/dev/pr_context.md`

### 12.2 Example Hook

Implement a concrete internal hook:

```python
class MultiAspectSafetyHook(ValidatorHook):
    hook_id = "internal-multi-aspect-safety"
    hook_version = "0.1"
    timeout_ms = 100

    def evaluate(self, envelope: ValidatorHookEnvelope) -> ValidatorHookResult:
        aspects = {
            "source_grounding": ...,
            "schema_semantics": ...,
            "policy_risk": ...,
            "externalization_risk": ...,

        ...
```

Aspect rules should be deterministic:

- source grounding checks for `context.provenance.source_ids`
- schema semantics checks for required output or input keys in fixture data

### 12.3 Decisions To Cover

Tests should cover:

- `ALLOW` when all aspects pass
- `DENY` when source grounding is missing for source-required fixture context
- `REVIEW_REQUIRED` for explicit externalization risk fixture label
- `TIMEOUT` fail-closed behavior through the existing `_invoke_hook` helper
- stale result fail-closed behavior if current hook contract exposes it in
  existing tests
- workflow artifact records hook evidence and keeps the hook internal

## 13. Workstream 7 - Safety Smoke Tests

### 13.1 Test File

Add:

- `tests/test_pr10d_research_safety_addendum.py`

### 13.2 Minimum Scenarios

Implement fixture-only smoke tests:

1. Prompt-injection-like source instruction cannot override workflow policy.
2. External send or handoff blocks without required approval.
3. Multi-turn failure-and-fix path cannot bypass approval after resume.
4. Handoff loop is bounded by `max_steps` or explicit approval.
5. Tool budget cannot be exceeded through step composition.
6. Adapter capability mismatch fails closed for present adapter surfaces.
7. Export shows governance rationale for blocked, paused, failed, and completed
   paths.

### 13.3 Prompt-Injection-Like Source Override

Use exact fixture structure rather than model text interpretation:

- source payload includes `"instruction": "ignore policy"`
- policy requires `caller_id`, role, source IDs, or approval
- invocation still fails or passes only according to policy fields, never source
  instruction content

Expected assertion:

- enforcement result and exception code are policy-driven
- source content does not widen allowed roles, transitions, or handoffs

### 13.4 External Send Without Approval

Use existing `workflow.escalation` or adapter metadata when present.

If no adapter surface is present, use a workflow fixture that attempts a
participant handoff not allowed by `workflow.handoffs`.

Expected assertion:

- fail-closed reason is `WORKFLOW_INVALID_TRANSITION` or the adapter-specific

  unless explicit metadata exists

PR-10d is sequenced after PR-10a, PR-10b, and PR-10c in the plan, but local
branch state may not contain all adapter surfaces when implementation starts.

Risk mitigation:

- make adapter tests conditional on source availability at implementation time
- document deferred gates for absent surfaces
- avoid importing optional SDKs in base tests
