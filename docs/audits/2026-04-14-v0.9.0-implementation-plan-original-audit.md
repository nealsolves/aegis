# Adversarial Review: `AIGC V0.9.0 IMPLEMENTATION_PLAN.md`

Date: 2026-04-14

Target reviewed: `docs/plans/AIGC V0.9.0 IMPLEMENTATION_PLAN.md`

## Verdict

The plan is directionally strong, but it is not implementation-ready as written.
The biggest problems are not "missing work"; they are contract mistakes and
internal contradictions that would harden the wrong behavior into the `v0.9.0`
beta surface.

Most serious issues:

1. The A2A section does not actually match the cited A2A 1.0 contract.
2. The Bedrock section does not fail closed on collaborator identity pinning.
3. Workflow policy composition widens permissions in a way that contradicts the
   published target-state design.
4. API/doc/release gates are too weak or too late for a beta that is already
   partially described in public design docs.

## Method

- Read the entire plan end-to-end.
- Cross-checked claims against the current repo state, public exports, CLI
  surface, release gating code, and target-state design docs.
- Verified protocol-specific claims against the cited primary sources:
  official A2A 1.0 specification and official Amazon Bedrock documentation.

## Findings

### 1. High: The A2A workstream is not protocol-correct against the A2A 1.0 spec it cites

The plan says the adapter should validate Agent Card `version` and enforce task
states named `SUBMITTED`, `WORKING`, `COMPLETED`, `FAILED`, `CANCELED`,
`INPUT_REQUIRED`, `REJECTED`, and `AUTH_REQUIRED`.

That is not what the A2A 1.0 spec says.

- The spec distinguishes the agent's top-level `version` from each interface's
  `protocolVersion`. `supportedInterfaces[].protocolVersion` is the protocol
  compatibility field; the top-level `version` is just the agent version.
- Version negotiation is driven by `A2A-Version` and the interface's supported
  `Major.Minor` protocol version.
- JSON enum values are serialized as the ProtoJSON enum names, e.g.
  `"TASK_STATE_INPUT_REQUIRED"`, not `"INPUT_REQUIRED"`.

Why this matters:

- A validator built from this plan can accept the wrong interface metadata,
  validate the wrong version field, and normalize the wrong state strings.
- Because these types are intended to become public beta surface, this is the
  kind of error that is expensive to fix after release.

What to change:

- Lock the adapter on `supportedInterfaces[].protocolVersion` plus
  `A2A-Version` handling, not on Agent Card `version`.
- Parse official `TASK_STATE_*` values first, then map them into internal AIGC
  enums if you want shorter internal names.
- Add explicit tests that reject cards/tasks using the wrong field or wrong enum
  namespace.

Evidence:

- Plan: `docs/plans/AIGC V0.9.0 IMPLEMENTATION_PLAN.md:13-16, 93-99, 231-239`
- A2A spec, AgentCard and AgentInterface: https://a2a-protocol.org/latest/specification/ sections 4.4.1 and 4.4.6
  - `supportedInterfaces` is required and ordered; `protocolVersion` is the interface protocol field.
  - top-level `version` is the agent version.
- A2A spec, versioning: https://a2a-protocol.org/latest/specification/ section 3.6
  - clients send `A2A-Version`; servers process requests using the requested `Major.Minor`.
- A2A spec, TaskState: https://a2a-protocol.org/latest/specification/ section 4.1.3
  - states are `TASK_STATE_SUBMITTED`, `TASK_STATE_WORKING`, `TASK_STATE_COMPLETED`, etc.
- A2A spec, JSON naming and enum serialization: https://a2a-protocol.org/latest/specification/ section 5.5
  - enum values serialize as their string names, e.g. `"TASK_STATE_INPUT_REQUIRED"`.

### 2. High: Bedrock collaborator pinning is not fail-closed if collaborator registry metadata is optional

The plan says explicit participants are required for safe collaborator pinning,
but the actual Bedrock adapter design does not enforce that strongly enough.

- The DSL example allows Bedrock collaborator policy by collaborator name only:
  `allowed_collaborators: [ResearchAgent, WriterAgent]`.
- Step 7 says the adapter accepts parsed `TracePart` payloads plus optional
  collaborator association metadata.
- The mapping rule binds `TracePart.collaboratorName` to `participant_id`.
- Later in the same step, the plan introduces a preflight validator for
  collaborator registry data that includes `agentDescriptor.aliasArn` and
  `relayConversationHistory`.

This is internally inconsistent. If collaborator registry metadata is optional,
alias-backed identity pinning is optional too. But the plan's own locked
decision says explicit participants are required for safe collaborator pinning.

Why this matters:

- Bedrock exposes both a human-chosen `collaboratorName` and a stronger
  collaborator alias ARN.
- Name-only policy pinning is weaker than alias-backed pinning and is more
  vulnerable to configuration drift or mistaken binding.
- A plan that allows Bedrock governance to proceed from trace name matching
  alone is not actually fail-closed on collaborator identity.

What to change:

- Make collaborator registry evidence mandatory whenever Bedrock handoffs are
  governed, not optional.
- Bind participants to alias-backed identity in manifests and policy, then use
  `collaboratorName` only as display/debug evidence.
- Treat missing alias-backed collaborator evidence as a protocol violation.

Evidence:

- Plan: `docs/plans/AIGC V0.9.0 IMPLEMENTATION_PLAN.md:16-19, 86-91, 210-223, 325`
- Amazon Bedrock `AssociateAgentCollaborator` API: https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent_AssociateAgentCollaborator.html
  - collaborator records include `collaboratorName`, `agentDescriptor.aliasArn`, and `relayConversationHistory`.
- Amazon Bedrock trace docs: https://docs.aws.amazon.com/bedrock/latest/userguide/trace-events.html
  - `TracePart` includes `collaboratorName`, while collaborator invocation input/output also include alias ARN fields.

### 3. High: Workflow composition semantics weaken governance by expanding roles

Step 5 says workflow composition should merge `allowed_agent_roles` by union.
That conflicts with the published target-state design, which says role sets must
compose by restriction, not implicit expansion.

Why this matters:

- Union semantics silently broaden the set of permitted actors when policies are
  composed.
- That is the opposite of conservative governance composition.
- It is especially risky here because the workflow DSL is intended to become the
  frozen public contract before adapter work begins.

What to change:

- Decide the role-composition rule before Step 5 lands.
- If the target-state design is correct, replace union semantics with a
  restrictive rule.
- Add adversarial tests that prove composition cannot widen participant
  permissions unexpectedly.

Evidence:

- Plan: `docs/plans/AIGC V0.9.0 IMPLEMENTATION_PLAN.md:189-194`
- Published target-state design: `docs/architecture/AIGC_HIGH_LEVEL_DESIGN.md:346-355`
  - "role sets compose by restriction, not implicit expansion"

### 4. Medium: Session lifecycle and workflow artifact status are internally inconsistent

Step 3 defines session lifecycle states as `OPEN`, `PAUSED`, `FAILED`,
`COMPLETED`, `CANCELED`, and `FINALIZED`. In the same step, the plan says that
closing a non-terminal context manager should emit an `INCOMPLETE` workflow
artifact. Step 2 defines a workflow artifact `status` field, but does not lock
its allowed values.

Why this matters:

- The plan is freezing schema and lifecycle in separate steps, but it has not
  defined the mapping between session states and emitted artifact statuses.
- `INCOMPLETE` is already being used as an artifact status even though it is not
  present in the locked lifecycle set.
- This is exactly the kind of ambiguity that causes incompatible fixtures,
  exporters, and readers.

What to change:

- Lock the full workflow artifact status enum before or with Step 2.
- Explicitly map session lifecycle states to artifact statuses.
- Decide whether `FINALIZED` is a lifecycle state, an artifact emission phase,
  or both. Right now it is overloaded.

Evidence:

- Plan: `docs/plans/AIGC V0.9.0 IMPLEMENTATION_PLAN.md:154, 166-170`

### 5. Medium: Public API and CLI contract protection happens too late

The repo already publishes a target-state design that names `GovernanceSession`,
`AgentIdentity`, `AgentCapabilityManifest`, `ValidatorHook`, and workflow CLI
commands. The current runtime exports none of those symbols and the current CLI
only implements `policy` and `compliance`. Despite that, the plan defers API
snapshot tests until Step 12.

Why this matters:

- The contract is already published in repo docs, so drift can start as soon as
  implementation PRs land.
- Without early contract tests, the beta surface can be defined accidentally by
  partial exports, provisional names, or mismatched docs long before the final
  hardening step.

What to change:

- Move public export and CLI contract tests up to Step 1 or Step 3.
- Gate every later workflow PR on those contract tests.
- Treat the high-level design doc as a contract input, not just a late
  documentation task.

Evidence:

- Plan: `docs/plans/AIGC V0.9.0 IMPLEMENTATION_PLAN.md:21-37, 283-289`
- Published design contract: `docs/architecture/AIGC_HIGH_LEVEL_DESIGN.md:23-32, 157-172, 419-423`
- Current public exports: `aigc/__init__.py:94-164`
- Current CLI surface: `aigc/_internal/cli.py:290-360`

### 6. Medium: The current doc-parity signal is too weak to rely on as a release baseline

The plan says "`976` tests collect, and doc parity currently passes." That is
true as a literal statement, but it masks a more important problem: the current
doc-parity gate can pass while real documentation facts are stale.

Current repo state:

- `README.md` still says `966 tests`.
- `doc_parity_manifest.yaml` also says `966`.
- Running `pytest --collect-only -q` on 2026-04-14 reported `976 tests collected`.
- The parity checker reads `test_count` from the manifest and checks docs
  against that manifest value; it does not derive test count from the actual
  suite.

Why this matters:

- Step 1 and Step 12 both lean on doc parity as a release-quality signal.
- Right now that signal is capable of false greens on baseline facts.
- If you do not fix the checker early, you will carry a misleading release gate
  into a beta that is already documentation-heavy.

What to change:

- Make doc parity derive test count from the real test suite, or stop checking
  test count in parity.
- Add a "manifest truth" audit in Step 1 before using doc parity as evidence.

Evidence:

- Plan: `docs/plans/AIGC V0.9.0 IMPLEMENTATION_PLAN.md:5-8, 145-147, 285, 307`
- README: `README.md:16-20`
- Manifest: `doc_parity_manifest.yaml:14-16`
- Parity checker implementation: `scripts/check_doc_parity.py:86-90, 117-120, 439-449`
- Local verification on 2026-04-14: `pytest --collect-only -q` -> `976 tests collected in 0.15s`

### 7. Low: Step 1 cannot achieve "one authoritative v0.9.0 plan" without explicit rename/archive work

Step 1 says to create `docs/plans/v0.9.0_IMPLEMENTATION_PLAN.md` and exit with
"one authoritative `v0.9.0` plan." But the repo already has multiple plan files
that overlap this space:

- `docs/plans/AIGC V0.9.0 IMPLEMENTATION_PLAN.md`
- `docs/plans/AIGC v0.9.0 to v1.0.0 PLAN.md`
- `implementation_plan.md`
- `implementation_status.md`

The step currently names new files to add, but does not explicitly name which
existing files get renamed, archived, or superseded.

Why this matters:

- The exit criterion is impossible without document inventory cleanup.
- This is exactly how planning drift becomes permanent.

What to change:

- In Step 1, explicitly rename or archive the current plan-under-review and any
  overlapping v0.9 planning docs.
- Update all references in release gates and tracking docs as part of the same
  change.

Evidence:

- Plan: `docs/plans/AIGC V0.9.0 IMPLEMENTATION_PLAN.md:145-149`
- Current repo inventory: `docs/plans/` contains the files listed above, and
  the repo root still contains `implementation_plan.md` and
  `implementation_status.md`.

## Recommended Rework Order

Before implementation starts, I would revise the plan in this order:

1. Correct the A2A contract lock: versioning, enum names, and field names.
2. Make Bedrock collaborator identity pinning alias-backed and mandatory.
3. Resolve the workflow composition rule so it cannot widen permissions.
4. Lock workflow/session status enums before any schema or exporter work.
5. Pull API/CLI contract tests and doc-parity hardening into the first third of
   the plan.
6. Clean up the planning document inventory so there is actually one
   authoritative `v0.9.0` plan.

## Bottom Line

The plan has the right overall decomposition, but it currently mixes one class
of issue that is easy to fix later (stale docs) with another class that is not
easy to fix later (public beta contract mistakes). The latter needs to be
repaired before implementation begins.
