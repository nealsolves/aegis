## Original Review

### Verdict

The plan is directionally strong, but it is not implementation-ready as written.
The biggest problems are not "missing work"; they are contract mistakes and
internal contradictions that would harden the wrong behavior into the `v0.9.0`
beta surface.

Most serious issues:

1. The A2A section does not actually match the cited A2A 1.0 contract.
2. The Bedrock section does not fail closed on collaborator identity pinning.
3. Workflow policy composition widens permissions in a way that contradicts the
   published target-state design.
4. API/doc/release gates are too weak or too late for a beta that is already
   partially described in public design docs.

### Method

- Read the entire plan end-to-end.
- Cross-checked claims against the current repo state, public exports, CLI
  surface, release gating code, and target-state design docs.
- Verified protocol-specific claims against the cited primary sources:
  official A2A 1.0 specification and official Amazon Bedrock documentation.

### 1. High: The A2A workstream is not protocol-correct against the A2A 1.0 spec it cites

The plan says the adapter should validate Agent Card `version` and enforce task
states named `SUBMITTED`, `WORKING`, `COMPLETED`, `FAILED`, `CANCELED`,
`INPUT_REQUIRED`, `REJECTED`, and `AUTH_REQUIRED`.

That is not what the A2A 1.0 spec says.

- The spec distinguishes the agent's top-level `version` from each interface's
  `protocolVersion`. `supportedInterfaces[].protocolVersion` is the protocol
  compatibility field; the top-level `version` is just the agent version.
- Version negotiation is driven by `A2A-Version` and the interface's supported
  `Major.Minor` protocol version.
- JSON enum values are serialized as the ProtoJSON enum names, e.g.
  `"TASK_STATE_INPUT_REQUIRED"`, not `"INPUT_REQUIRED"`.

Why this matters:

- A validator built from this plan can accept the wrong interface metadata,
  validate the wrong version field, and normalize the wrong state strings.
- Because these types are intended to become public beta surface, this is the
  kind of error that is expensive to fix after release.

What to change:

- Lock the adapter on `supportedInterfaces[].protocolVersion` plus
  `A2A-Version` handling, not on Agent Card `version`.
- Parse official `TASK_STATE_*` values first, then map them into internal AEGIS
  enums if you want shorter internal names.
- Add explicit tests that reject cards/tasks using the wrong field or wrong enum
  namespace.

Evidence:

- Plan: `docs/plans/AEGIS V0.9.0 IMPLEMENTATION_PLAN.md:13-16, 93-99, 231-239`
- A2A spec, AgentCard and AgentInterface: https://a2a-protocol.org/latest/specification/ sections 4.4.1 and 4.4.6
  - `supportedInterfaces` is required and ordered; `protocolVersion` is the interface protocol field.
  - top-level `version` is the agent version.
- A2A spec, versioning: https://a2a-protocol.org/latest/specification/ section 3.6
  - clients send `A2A-Version`; servers process requests using the requested `Major.Minor`.
- A2A spec, TaskState: https://a2a-protocol.org/latest/specification/ section 4.1.3
  - states are `TASK_STATE_SUBMITTED`, `TASK_STATE_WORKING`, `TASK_STATE_COMPLETED`, etc.
- A2A spec, JSON naming and enum serialization: https://a2a-protocol.org/latest/specification/ section 5.5
  - enum values serialize as their string names, e.g. `"TASK_STATE_INPUT_REQUIRED"`.

> **Extended Review — Finding 1:** The original review correctly identified both the
> task state naming error and the version field error as one combined A2A protocol
> finding. On closer inspection these are two independent defects that should be fixed
> separately and tested independently.
>
> **Task state names:** The plan's Shared Internal Event Model (lines 123–136) locks
> `SUBMITTED`, `WORKING`, etc. as canonical values. These are used throughout the
> adapter spec in Step 8 (lines 233–237) as the pause/escalation trigger values. An
> adapter built on shortened names will fail to parse real A2A 1.0 payloads at the
> state machine level.
>
> **Version negotiation:** Step 8 says "validate Agent Card fields against A2A 1.0
> features actually required by the adapter: `supportedInterfaces`, `version`..."
> (line 229). Reading `version` as the protocol compatibility field is incorrect.
> `supportedInterfaces[i].protocolVersion` is the per-interface protocol field;
> `A2A-Version` is the HTTP header used for negotiation (§3.6). A validator that
> checks the top-level `version` field will incorrectly accept cards from agents that
> list only an agent version without a matching `protocolVersion` in their interface
> list.
>
> Both defects must be fixed before Step 8. They have separate test implications:
> one requires state machine fixture tests; the other requires Agent Card schema
> validation tests.

### 2. High: Bedrock collaborator pinning is not fail-closed if collaborator registry metadata is optional

The plan says explicit participants are required for safe collaborator pinning,
but the actual Bedrock adapter design does not enforce that strongly enough.

- The DSL example allows Bedrock collaborator policy by collaborator name only:
  `allowed_collaborators: [ResearchAgent, WriterAgent]`.
- Step 7 says the adapter accepts parsed `TracePart` payloads plus optional
  collaborator association metadata.
- The mapping rule binds `TracePart.collaboratorName` to `participant_id`.
- Later in the same step, the plan introduces a preflight validator for
  collaborator registry data that includes `agentDescriptor.aliasArn` and
  `relayConversationHistory`.

This is internally inconsistent. If collaborator registry metadata is optional,
alias-backed identity pinning is optional too. But the plan's own locked
decision says explicit participants are required for safe collaborator pinning.

Why this matters:

- Bedrock exposes both a human-chosen `collaboratorName` and a stronger
  collaborator alias ARN.
- Name-only policy pinning is weaker than alias-backed pinning and is more
  vulnerable to configuration drift or mistaken binding.
- A plan that allows Bedrock governance to proceed from trace name matching
  alone is not actually fail-closed on collaborator identity.

What to change:

- Make collaborator registry evidence mandatory whenever Bedrock handoffs are
  governed, not optional.
- Bind participants to alias-backed identity in manifests and policy, then use
  `collaboratorName` only as display/debug evidence.
- Treat missing alias-backed collaborator evidence as a protocol violation.

Evidence:

- Plan: `docs/plans/AEGIS V0.9.0 IMPLEMENTATION_PLAN.md:16-19, 86-91, 210-223, 325`
- Amazon Bedrock `AssociateAgentCollaborator` API: https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent_AssociateAgentCollaborator.html
  - collaborator records include `collaboratorName`, `agentDescriptor.aliasArn`, and `relayConversationHistory`.
- Amazon Bedrock trace docs: https://docs.aws.amazon.com/bedrock/latest/userguide/trace-events.html
  - `TracePart` includes `collaboratorName`, while collaborator invocation input/output also include alias ARN fields.

> **Extended Review — Finding 2:** The original review is correct and the internal
> inconsistency is real. The plan's locked decision (line 17: "Workflow participant
> identity is explicit in policy because role-only rules are insufficient for safe
> Bedrock and A2A governance") cannot coexist with Step 7's `optional` qualifier on
> collaborator association metadata.
>
> The additional precision from the extended review: the `optional` framing creates
> a fail-open path specifically because the **preflight validator** that checks alias
> ARNs is positioned as a separate component from the core adapter logic. Callers who
> skip preflight, or implementations that treat preflight as an optional configuration
> step, will proceed on name-only evidence. The fix is not just making the evidence
> mandatory in prose — it must be enforced in the adapter's authorization path so it
> cannot be skipped regardless of how the host configures preflight.

### 3. High: Workflow composition semantics weaken governance by expanding roles

Step 5 says workflow composition should merge `allowed_agent_roles` by union.
That conflicts with the published target-state design, which says role sets must
compose by restriction, not implicit expansion.

Why this matters:

- Union semantics silently broaden the set of permitted actors when policies are
  composed.
- That is the opposite of conservative governance composition.
- It is especially risky here because the workflow DSL is intended to become the
  frozen public contract before adapter work begins.

What to change:

- Decide the role-composition rule before Step 5 lands.
- If the target-state design is correct, replace union semantics with a
  restrictive rule.
- Add adversarial tests that prove composition cannot widen participant
  permissions unexpectedly.

Evidence:

- Plan: `docs/plans/AEGIS V0.9.0 IMPLEMENTATION_PLAN.md:189-194`
- Published target-state design: `docs/architecture/AEGIS_HIGH_LEVEL_DESIGN.md:346-355`
  - "role sets compose by restriction, not implicit expansion"

> **Extended Review — Finding 3:** Confirmed and no correction required. One additional
> context point: the existing invocation-level policy composition system
> (`ARCHITECTURAL_INVARIANTS.md` §9, `policy_loader.py`) uses `composition_strategy`
> with explicit `union`/`intersect`/`replace` modes. The workflow DSL is a new surface
> and the composition rule for its fields has never been explicitly locked in an ADR.
> The conflict between the plan (union) and the HLD (restriction) must be resolved in
> an ADR before Step 5 starts — not by choosing a default silently in implementation.
>
> Specific line references:
> - Plan line 191: `allowed_agent_roles` union
> - HLD §8.3 (approx. line 346–355): "role sets compose by restriction"
>
> The plan also says `allowed_transitions` merges by `from` key — this is a
> dictionary-style merge, not union. It is worth confirming whether this merge is also
> restrictive (taking the intersection of allowed `to` values) or additive. The plan
> does not specify.

### 4. Medium: Session lifecycle and workflow artifact status are internally inconsistent

Step 3 defines session lifecycle states as `OPEN`, `PAUSED`, `FAILED`,
`COMPLETED`, `CANCELED`, and `FINALIZED`. In the same step, the plan says that
closing a non-terminal context manager should emit an `INCOMPLETE` workflow
artifact. Step 2 defines a workflow artifact `status` field, but does not lock
its allowed values.

Why this matters:

- The plan is freezing schema and lifecycle in separate steps, but it has not
  defined the mapping between session states and emitted artifact statuses.
- `INCOMPLETE` is already being used as an artifact status even though it is not
  present in the locked lifecycle set.
- This is exactly the kind of ambiguity that causes incompatible fixtures,
  exporters, and readers.

What to change:

- Lock the full workflow artifact status enum before or with Step 2.
- Explicitly map session lifecycle states to artifact statuses.
- Decide whether `FINALIZED` is a lifecycle state, an artifact emission phase,
  or both. Right now it is overloaded.

Evidence:

- Plan: `docs/plans/AEGIS V0.9.0 IMPLEMENTATION_PLAN.md:154, 166-170`

> **Extended Review — Finding 4:** Confirmed. The `FINALIZED` overloading problem
> noted in the original review is real. Additional precision: the HLD §7.1 also
> defines the same six lifecycle states (`OPEN`, `PAUSED`, `FAILED`, `COMPLETED`,
> `CANCELED`, `FINALIZED`) with no `INCOMPLETE`. The discrepancy runs through both
> the plan and its own reference design.
>
> The fix must happen before Step 2, not alongside it. Step 2 writes the schema.
> If `INCOMPLETE` is not locked as a valid status value before the schema is written,
> it will be either missing from the schema (causing validation failures when it is
> later emitted) or added retroactively (requiring a schema bump). Either outcome
> is avoidable by locking the enum first.
>
> There is also a secondary ambiguity not raised in the original review: context
> manager exception semantics. See Finding 10 in the New Findings section below.

### 5. Medium: Public API and CLI contract protection happens too late

The repo already publishes a target-state design that names `GovernanceSession`,
`AgentIdentity`, `AgentCapabilityManifest`, `ValidatorHook`, and workflow CLI
commands. The current runtime exports none of those symbols and the current CLI
only implements `policy` and `compliance`. Despite that, the plan defers API
snapshot tests until Step 12.

Why this matters:

- The contract is already published in repo docs, so drift can start as soon as
  implementation PRs land.
- Without early contract tests, the beta surface can be defined accidentally by
  partial exports, provisional names, or mismatched docs long before the final
  hardening step.

What to change:

- Move public export and CLI contract tests up to Step 1 or Step 3.
- Gate every later workflow PR on those contract tests.
- Treat the high-level design doc as a contract input, not just a late
  documentation task.

Evidence:

- Plan: `docs/plans/AEGIS V0.9.0 IMPLEMENTATION_PLAN.md:21-37, 283-289`
- Published design contract: `docs/architecture/AEGIS_HIGH_LEVEL_DESIGN.md:23-32, 157-172, 419-423`
- Current public exports: `aegis/__init__.py:94-164`
- Current CLI surface: `aegis/_internal/cli.py:290-360`

> **Extended Review — Finding 5:** Confirmed and strengthened. The original review
> correctly identifies the deferred-test risk. One additional dimension: the existing
> `tests/test_public_api.py` currently validates the v0.3.3 surface only. It has no
> assertions for the new workflow symbols. During Steps 3–11, every PR that adds a new
> export will be self-certifying — there is no external contract anchor that would
> catch a symbol named `GovernanceSession` in the plan but `WorkflowSession` in the
> implementation.
>
> A concrete minimal fix that avoids large upfront work: add a "not yet exported"
> snapshot test in Step 1 that explicitly asserts the new workflow symbols are absent.
> As each step lands, update those assertions to "must be exported." This creates a
> continuous contract signal across 11 PRs at near-zero implementation cost.

### 6. Medium: The current doc-parity signal is too weak to rely on as a release baseline

The plan says "`976` tests collect, and doc parity currently passes." That is
true as a literal statement, but it masks a more important problem: the current
doc-parity gate can pass while real documentation facts are stale.

Current repo state:

- `README.md` still says `966 tests`.
- `doc_parity_manifest.yaml` also says `966`.
- Running `pytest --collect-only -q` on 2026-04-14 reported `976 tests collected`.
- The parity checker reads `test_count` from the manifest and checks docs
  against that manifest value; it does not derive test count from the actual
  suite.

Why this matters:

- Step 1 and Step 12 both lean on doc parity as a release-quality signal.
- Right now that signal is capable of false greens on baseline facts.
- If you do not fix the checker early, you will carry a misleading release gate
  into a beta that is already documentation-heavy.

What to change:

- Make doc parity derive test count from the real test suite, or stop checking
  test count in parity.
- Add a "manifest truth" audit in Step 1 before using doc parity as evidence.

Evidence:

- Plan: `docs/plans/AEGIS V0.9.0 IMPLEMENTATION_PLAN.md:5-8, 145-147, 285, 307`
- README: `README.md:16-20`
- Manifest: `doc_parity_manifest.yaml:14-16`
- Parity checker implementation: `scripts/check_doc_parity.py:86-90, 117-120, 439-449`
- Local verification on 2026-04-14: `pytest --collect-only -q` -> `976 tests collected in 0.15s`

> **Extended Review — Finding 6:** The original review's test count claim ("976 tests
> collected") now needs its own correction. On 2026-04-14, `grep -rn "def test_"
> tests/ | wc -l` returns **963 test functions** across 73 test files. The plan says
> 976; README says 966; manifest says 966; grep-based count is 963. All four values
> differ.
>
> The likely explanation: pytest collects parametrized test cases as separate items,
> so the "976 collected" figure from pytest's `--collect-only` mode inflates the count
> relative to the raw function count. The manifest and README were last updated for
> v0.3.2 (818 tests) and never updated for v0.3.3. This makes the original review's
> claim that "976 tests collected" is correct as a pytest count, but it renders the
> 966 figure in README and manifest even more stale.
>
> The core finding stands: the parity checker validates docs against the manifest
> value, not the live pytest output. The gap is now confirmed to be three-way: plan
> (976 pytest), manifest/README (966), raw function count (963). None of these
> match. See also Finding 7 in the New Findings section on the companion plan
> carrying the same wrong value.

1. Correct the A2A contract lock: versioning, enum names, and field names.

### 8. Medium: `SessionPreCallResult` Wrapping Semantics Are Underspecified

**Step affected:** Step 4 (PR-04)

Step 4 says:

> add `SessionPreCallResult` as a thin wrapper around existing `PreCallResult`;
> do not overload the legacy token type with session-only state
> — Plan line 179

`PreCallResult` has a process-local HMAC-signed consumption model (established in
ADR-0009 and hardened in the 2026-04-05 security audit):
- One-time use enforced by a `_consumed` flag
- `_consumed` is validated and flipped via `object.__setattr__` on first use
- Replay via cloned tokens blocked by a process-local consumption registry
- Phase B reads `_frozen_evidence_bytes` (HMAC-signed) rather than mutable state

The plan does not specify how `SessionPreCallResult` interacts with this model:

1. **Double-consumption risk**: Can the inner `PreCallResult` be consumed
   independently via module-level `enforce_post_call()`? If yes, the session context
   is bypassed. If no, the enforcement mechanism is not specified.
2. **Consumption ownership**: Is one-time-use enforced on the outer wrapper, the inner
   token, or both? Two tokens with independent consumption tracking create undefined
   composability.
3. **HMAC signing boundary**: `PreCallResult._frozen_evidence_bytes` is HMAC-signed
   using the session key at Phase A. Does `SessionPreCallResult` sign session-level
   metadata separately, or does it rely entirely on the inner token's HMAC?

Without specifying these semantics, Step 4 will produce a correct-looking wrapper that
can be misused in ways that bypass session-level governance.

**Evidence:**
- Plan: lines 178–180 (Step 4 `SessionPreCallResult` spec)
- ADR-0009: `docs/decisions/ADR-0009-split-enforcement-model.md`, §4, §5, §7
- Security hardening: `CHANGELOG.md` v0.3.2 security section, Findings 1–5
- Current implementation: `aegis/_internal/enforcement.py` (HMAC and consumption model)

**Fix required before Step 4:** Define explicitly whether `SessionPreCallResult`
owns or delegates consumption tracking, and specify the HMAC signing boundary.

### 9. Medium: Tool Budget Counting From Adapter Events Is Underspecified

**Step affected:** Step 6 (PR-06)

Step 6 says:

> Count tool budgets from invocation `tool_calls` for local steps and from normalized
> adapter events for Bedrock/A2A observational steps
> — Plan line 202

The shared event model defines a `usage` metadata field (line 120) and `tool_observed`
as an event kind (line 130), but the plan does not specify:

1. **Unit of cost per event**: Does one `tool_observed` event consume 1 unit of
   `max_total_tool_calls`? A single Bedrock trace may produce many `ACTION_GROUP`
   observations from one supervisor invocation.
2. **Normalization between step types**: A local step's `tool_calls` is a field on the
   invocation dict. A Bedrock adapter's tool count is inferred from observation events.
   These are structurally different paths with no stated normalization rule.
3. **Evaluation timing**: Is `max_total_tool_calls` enforced at step authorization
   (before execution) or at step completion (after the trace is available)? If checked
   before execution, the trace hasn't arrived yet. If after, the step already ran.

`WORKFLOW_BUDGET_EXCEEDED` is specified as a hard enforcement failure reason. An
underspecified counting rule means the same workflow will hit the budget at different
points depending on step type.

**Evidence:**
- Plan: lines 110–120 (event model `usage` field), 130 (`tool_observed`), 202 (budget
  counting spec)

**Fix required before Step 6:** Define budget counting unit, normalization rule, and
evaluation point for each step type (local, Bedrock, A2A).

### 10. Medium: `GovernanceSession` Context Manager Exception Semantics Are Undefined

**Step affected:** Step 3 (PR-03)

Step 3 says:

> make `GovernanceSession` a context manager; on clean terminal exit it finalizes
> automatically; if closed while non-terminal it emits an `INCOMPLETE` workflow
> artifact rather than silently dropping session evidence
> — Plan lines 168–169

Python context managers exit via two paths: normal (`__exit__` called with
`(None, None, None)`) and exception (`__exit__` called with a live exception).
The plan uses "clean terminal exit" without defining which path this refers to.

Unresolved questions:
1. If the `with` block exits due to an unhandled exception, does `__exit__` finalize
   normally or emit `INCOMPLETE`?
2. If in-progress steps exist when an exception exits the block, what state do
   those steps enter?
3. Does `GovernanceSession.__exit__` suppress exceptions or always re-raise?
4. If the session is already `FINALIZED` when `__exit__` is called, is that
   idempotent or an error?

Any integration that wraps a workflow in error-handling code will hit one of these
paths. Without a spec, different implementers will make different choices and the
resulting behavior will silently diverge.

**Evidence:**
- Plan: lines 167–170

**Fix required before Step 3:** Specify `__exit__` behavior for each combination of
session state × normal vs. exception exit.

### 11. Medium: `AEGIS.open_session()` Creates an Undocumented Migration Requirement

**Step affected:** Step 3 (PR-03), Step 12 (PR-12)

Step 3 specifies:

> add `AEGIS.open_session(...)` as the only public constructor entrypoint
> — Plan line 167

The current SDK has two coexisting usage patterns: module-level
(`enforce_invocation(invocation)`) and instance-scoped (`AEGIS(...).enforce(invocation)`).
If `GovernanceSession` is only constructable via `AEGIS.open_session()`, workflow
governance requires adopting the instance-scoped API. Users who currently use only
`enforce_invocation` must create an `AEGIS` instance to access any workflow feature.

This is a meaningful adoption barrier that is not listed in the migration implications
section of the plan and not covered in `MIGRATION_0_3_3_TO_0_9` (which is listed as
a new document to create but is not yet written). The plan frames this as an
implementation detail ("session behavior inherits instance-scoped config"), but from
a user perspective it is an API pattern change.

**Evidence:**
- Plan: lines 22, 167
- HLD: `docs/architecture/AEGIS_HIGH_LEVEL_DESIGN.md`, §13.1
- Current public surface: `aegis/__init__.py` exports `enforce_invocation` without
  requiring an `AEGIS` instance

**Fix required:** Document the API pattern requirement explicitly in the Step 1
migration document. Evaluate whether a module-level `open_session()` convenience
function is warranted for parity with `enforce_invocation`.

### 12. Low: Version Jump From `0.3.3` to `0.9.0` Has No Stated Justification

**Step affected:** Step 12 (PR-12), all release framing

The plan proposes jumping from `v0.3.3` directly to `v0.9.0`. Under Semantic
Versioning, the next minor bump from `0.3.3` is `0.4.0`. The plan gives no rationale
for skipping `0.4.x` through `0.8.x`. The implied rationale visible in the companion
plan (`AEGIS v0.9.0 to v1.0.0 PLAN.md`, lines 6–8) is that `0.9.0` signals
"feature-complete beta near 1.0". That is a reasonable intent, but:

- Users who pin `>=0.3.3,<1.0.0` would receive `0.9.0` even if their intent was
  conservative patch-level updates to the `0.3.x` line
- No ADR or migration document explains the version jump to contributors or adopters
- Neither `RELEASE_GATES.md` nor the updated `CHANGELOG.md` currently address this

**Evidence:**
- Plan: line 286 (version bump to `0.9.0`)
