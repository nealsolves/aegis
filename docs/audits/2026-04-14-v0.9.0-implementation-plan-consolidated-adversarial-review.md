## Verdict

The plan has the right overall decomposition. Steps 1 through 6 are ordered sensibly,
the adapter steps are correctly downstream of the shared workflow core, and the plan is
careful about preserving the SDK boundary.

It is still not implementation-ready as written. The strongest problems are:

1. The A2A contract lock is not aligned with the cited A2A 1.0 contract.
2. The Bedrock collaborator identity model is not fail-closed enough for the plan's own
   participant-pinning goals.
3. The workflow DSL composition rule conflicts with the published target-state design.
4. The lifecycle/evidence contract is underspecified where it matters most: status
   values, public API freeze points, and release-truth gating.

## Confirmed Findings

### 1. Critical: The A2A contract lock is wrong at the wire level

The plan's A2A section mixes descriptive Agent Card fields with wire-compatibility
fields and uses shortened task-state names where the 1.0 contract uses full ProtoJSON
enum names.

Problem areas in the plan:

- Step 8 treats Agent Card `version` as part of the required validation surface
  without separating it from the actual protocol compatibility field,
  `supportedInterfaces[].protocolVersion`.
- Step 8 uses `SUBMITTED`, `WORKING`, `COMPLETED`, `FAILED`, `CANCELED`,
  `INPUT_REQUIRED`, `REJECTED`, and `AUTH_REQUIRED` as the A2A state rules.

Why this matters:

- A validator built to the plan can conflate descriptive agent version metadata with
  protocol compatibility.
- A parser built to the plan can accept or emit non-wire values for task state.
- These are beta-surface problems, not implementation details. If they land, they are
  expensive to fix later.

Correction:

- Treat `supportedInterfaces[].protocolVersion` as the compatibility field.
- Validate host-supplied `A2A-Version` request metadata where version negotiation is in
  scope; do not shift transport ownership into the adapter.
- Parse and validate `TASK_STATE_*` values from the wire, then map them to shorter
  internal names only if the implementation wants an internal enum.

### 2. High: Bedrock collaborator identity pinning is not fail-closed enough

The plan says explicit participants are required because role-only rules are insufficient
for safe Bedrock governance, but the actual Bedrock design still leaves too much room for
name-only matching.

The weak points are:

- The workflow DSL example pins Bedrock collaborators by human-readable names only:
  `allowed_collaborators: [ResearchAgent, WriterAgent]`.
- Step 7 says the adapter accepts parsed `TracePart` payloads plus optional collaborator
  association metadata.
- Step 7 binds `TracePart.collaboratorName` to `participant_id`.
- Step 7 also references stronger alias-backed evidence through collaborator metadata,
  but does not make alias-backed identity mandatory in the authorization path.

Why this matters:

- Bedrock exposes both a display name and alias-backed identity evidence.
- A design that can proceed on `collaboratorName` alone does not meet the plan's own
  safe-pinning requirement.
- The exact mechanism can vary, but the plan needs a locked rule that participant
  binding uses alias-backed evidence when handoffs are governed.

Correction:

- Make alias-backed collaborator identity mandatory for governed Bedrock handoffs.
- Allow that evidence to come from host-supplied collaborator metadata and, where
  available, trace collaborator invocation fields.
- Use `collaboratorName` as descriptive evidence only, not as the sole binding key.

### 3. High: Workflow composition semantics conflict with the published HLD

Step 5 says workflow composition should merge `allowed_agent_roles` by union and
`allowed_transitions` by `from`. The published high-level design says workflow
composition is conservative: role sets compose by restriction, transition and handoff
rules remain explicit, and ambiguity fails validation rather than choosing a permissive
default.

Why this matters:

- Union widens permissions.
- `merge by from` is incomplete unless the `to` sets are defined restrictively or
  ambiguity fails validation.
- The workflow DSL is supposed to be frozen before the workflow engine and adapters land.
  This is exactly the stage where the rule must be unambiguous.

Correction:

- Resolve both role and transition composition semantics before Step 5.
- If the HLD is the intended contract, replace union semantics with a restrictive rule
  and require explicit post-composition transition sets.
- Add adversarial tests that prove child workflow policies cannot widen either the
  parent role envelope or the allowed transition envelope unexpectedly.

### 4. High: Workflow lifecycle and emitted artifact status are not locked coherently

The plan defines session lifecycle states as `OPEN`, `PAUSED`, `FAILED`, `COMPLETED`,
`CANCELED`, and `FINALIZED`, but then says a non-terminal close emits an `INCOMPLETE`
workflow artifact. The workflow artifact `status` field is introduced before its allowed
values are locked.

Why this matters:

- `INCOMPLETE` is already being used as an artifact outcome but is not part of the
  locked lifecycle set.
- `FINALIZED` reads as both a state and an emission phase.
- Step 2 writes schema before the plan defines the full state-to-status mapping.

Correction:

- Lock the workflow artifact `status` enum before Step 2 writes schema.
- Explicitly map session lifecycle states to emitted artifact statuses.
- Decide whether `FINALIZED` is a steady state, an emission action, or both.

### 5. Medium: Public API and CLI contract protection happens too late

The repo already publishes a target public surface for 1.0.0, but the plan defers public
API snapshot tests until Step 12.

Current state:

- The HLD already names `GovernanceSession`, `SessionPreCallResult`, `AgentIdentity`,
  `AgentCapabilityManifest`, `ValidatorHook`, `BedrockTraceAdapter`, `A2AAdapter`, and
  workflow CLI commands.
- The current public package exports none of those names.
- The current CLI only exposes `policy` and `compliance`.
- Current public API tests only cover the `v0.3.3` surface.

Why this matters:

- The contract is already published in the repo.
- Without earlier contract tests, names and CLI shapes can drift through most of the
  implementation train before the hardening step catches anything.

Correction:

- Move workflow-surface contract tests forward.
- Add staged public-surface and CLI-shape tests in the first third of the plan:
  assert absence for symbols and commands that are intentionally not landed yet, then
  promote those assertions to presence in the PR that introduces each contract.

## Open Questions The Plan Should Resolve Before Implementation

These are not promoted to top findings because they are design ambiguities more than
proven contract mistakes, but they should still be resolved before implementation.

### A. `SessionPreCallResult` vs `PreCallResult`

Step 4 introduces `SessionPreCallResult` as a thin wrapper around the existing
security-hardened `PreCallResult`, but does not say whether the wrapped token can still
be consumed independently through module-level `enforce_post_call`. That leaves a
concrete double-consumption or session-bypass question, plus replay and signing
semantics for the wrapper itself.

## Strengths

- The core sequencing is good: workflow evidence, session core, step enforcement, DSL,
  engine, then adapters is the right dependency order.
- The plan is explicit about boundary discipline: the host owns orchestration,
  transport, credentials, retries, and business state.
- The additive-evidence posture is right: workflow evidence supplements invocation
  evidence instead of replacing it.
- The adapter steps correctly forbid live provider calls in tests.

## Recommended Rework Order

1. Fix the A2A contract lock before Step 8 starts.
2. Make Bedrock participant binding explicitly alias-backed before Step 7 starts.
3. Resolve workflow composition semantics before Step 5 starts.
4. Lock workflow artifact status values before Step 2 writes schema.
5. Pull public-surface and CLI contract tests forward from Step 12.
6. Fix Step 1 so it explicitly cleans up competing plans and stale tracker docs.
7. Tighten the parity gate so it does not certify stale baseline facts as current.

Lower-severity issues from the superseded review, especially release-signaling around
`0.3.3 -> 0.9.0` and the distribution of documentation work, remain worth cleaning up
but are intentionally not treated here as pre-implementation blockers.

## Bottom Line

This plan should be treated as a strong draft, not as ready-to-execute implementation
guidance. Its main weakness is not sequencing; it is contract precision. The protocol
locks, workflow composition rules, lifecycle/status rules, and release-truth gates need
to be tightened before code starts landing.
