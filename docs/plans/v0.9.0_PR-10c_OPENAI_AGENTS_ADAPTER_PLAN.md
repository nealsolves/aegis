# `v0.9.0` PR-10c OpenAI Agents SDK Adapter Plan

Date: 2026-04-20
Status: Proposed
Target branch: `feat/v0.9-10-openai-agents-adapter`

---

## Goal

Add an optional AIGC adapter for applications that use the OpenAI Agents SDK
(`openai-agents` / `openai-agents-python`) while preserving the existing
`v0.9.0` beta boundary:

- the host still owns `Runner`, sessions, providers, transport, tool
  execution, approvals, and business control flow
- AIGC still owns governance, fail-closed checks, and emitted evidence
- the default adopter path still succeeds without any adapter

Naming rule for this repo:

- "OpenAI-SDK adapter" in PR-10c means the OpenAI Agents SDK runtime described
  at `https://github.com/openai/openai-agents-python` and
  `https://developers.openai.com/api/docs/guides/agents`
- it does not mean a new wrapper around raw Responses API usage, which remains
  governable through the existing host-owned invocation and workflow APIs

## Repo Baseline At Authoring Time

- PR-01 through PR-09 are complete on `develop`.
- `GovernanceSession`, `SessionPreCallResult`, `workflow trace`, and
  `workflow export` already ship in the source-only `v0.9.0` beta line.
- `workflow.protocol_constraints` currently recognizes `local`, `bedrock`, and
  `a2a`, but not an OpenAI Agents protocol family.
- Session tool budgets are currently enforced at step pre-call time from the
  invocation's declared `tool_calls` list.
- Workflow artifact step records currently store only:
  - `step_id`
  - `participant_id`
  - `invocation_artifact_checksum`
- `AgentIdentity`, `AgentCapabilityManifest`, `BedrockTraceAdapter`, and
  `A2AAdapter` still remain planned-only surfaces.

Implication:

- PR-10c cannot be only a thin result-normalization helper.
- It needs a small additive session/runtime seam for dynamic in-run tool
  authorization and post-run step metadata.

## PR-10c Contract

- The adapter remains optional and ships behind an optional dependency extra.
- Base `aegis` install must not require `openai-agents`.
- The host still calls `Runner.run(...)`, `Runner.run_sync(...)`, or
  `Runner.run_streamed(...)` directly.
- The adapter does not own:
  - model selection
  - provider credentials
  - OpenAI session storage
  - retries
  - streaming transport
  - approval decisions
  - remote orchestration
- The adapter does normalize:
  - participant binding evidence
  - declared handoff graph
  - run/result summaries
  - optional trace summaries
  - human-interruption metadata
  - dynamic tool-call governance events when the host uses adapter-managed
    wrappers
- Fail-closed behavior is mandatory when required evidence is missing,
  ambiguous, or unsupported.

Important scope line:

- PR-10c targets the OpenAI Agents SDK runtime.
- Raw single-call Responses API usage stays on the existing AIGC invocation or
  workflow path and is not re-wrapped by this adapter.

## Supported Surface In PR-10c

Supported initially:

- `Agent`
- `Runner.run(...)`
- `Runner.run_sync(...)`
- `Runner.run_streamed(...)` once the run reaches a terminal result
- `RunResult` / `RunResultStreaming`
- `RunState` resume after interruptions
- `handoffs`
- `Agent.as_tool(...)`
- function tools, when registered through adapter-managed wrappers
- SDK sessions as host-owned memory, recorded only as metadata
- tracing via custom trace processors
- `RunContextWrapper.context` as the local-only carrier for AIGC correlation

Explicitly out of initial PR-10c scope:

- `RealtimeAgent`
- voice pipeline / realtime voice orchestration
- `SandboxAgent`
- hosted tools and built-in execution tools where AIGC cannot authorize
  execution before side effects
- hosted MCP and tool-search surfaces
- automatic governance of arbitrary third-party processors or runtime plugins

Fail-closed rule for unsupported surfaces:

- if policy requires governed tool or protocol evidence and the run uses an
  unsupported OpenAI Agents surface, binding or execution must reject with an
  explicit workflow protocol violation

  parallel optional-adapter track after PR-10b.

### 2. Public Adapter Surface

Add a minimal public surface:

- `OpenAIAgentsAdapter`
- `OpenAIAgentsTracingProcessor`

Design preference:

- reuse shared `AgentIdentity` and `AgentCapabilityManifest` work rather than
  inventing OpenAI-only public identity types
- keep OpenAI-specific binding details inside the adapter and manifest payloads

### 3. Policy / Protocol Surface

Add additive support for:

- `workflow.protocol_constraints.openai_agents`
- participant protocol declarations that include `openai_agents`

Initial runtime checks should cover:

- explicit participant binding for each governed root agent
- unique trace-visible agent identity for the governed graph
- trace-required vs trace-optional policy behavior
- unsupported surface rejection
- declared handoff graph validation before the run

### 4. Dynamic Tool Governance Seam

PR-10c needs one additive session-level seam because the OpenAI Agents SDK can
decide tool usage dynamically inside a run.

Planned additive behavior:

- a public or adapter-reachable step-level tool-authorization hook on
  `GovernanceSession`
- adapter-managed wrappers for:
  - function tools
  - `Agent.as_tool(...)`
- immediate budget / allowlist rejection before wrapped tool execution

Out-of-scope first-cut behavior:

- silent post-hoc-only counting for tools that AIGC cannot intercept

### 5. Post-Run Step Metadata

Add an additive way to attach normalized adapter metadata to workflow step
records after the run completes.

Expected metadata categories:

- protocol family and adapter version
- trace correlation ids
- agent sequence summary
- observed handoffs
- observed tool-call summary
- interruption / approval summary
- models seen
- usage summary

The default persistence rule remains:

- do not persist raw prompts, raw tool inputs, or raw trace payloads by default
- persist only redacted or summary-form metadata unless the host explicitly
  opts into richer evidence

### 6. Docs And Advanced Recipe

Create advanced follow-on documentation only, not first-adopter docs:

- `docs/reference/external/OPENAI_AGENTS_ADAPTER.md`

The recipe should show:

- host-owned `Runner` usage
- session opening through `AIGC.open_session(...)`
- adapter-managed tool wrappers
- optional trace processor wiring
- interruption pause/resume flow

### 7. Tests

Required test groups:

- fixture-only adapter normalization tests
- participant-binding and duplicate-name rejection tests
- declared-handoff-graph validation tests
- trace-required / trace-missing fail-closed tests
- function-tool wrapper governance tests
- `Agent.as_tool(...)` wrapper governance tests

## Sequencing And Risk Notes

- PR-10c should reuse common optional-adapter patterns established in PR-10a and
  PR-10b where that reduces duplication.
- The biggest design risk is pretending dynamic in-run tool execution can be
  governed with the current pre-call-only `tool_calls` shape. It cannot.
- The second biggest risk is over-claiming support for OpenAI Agents features
  that do not expose a safe pre-execution governance hook.
- The third risk is leaking raw trace payloads into AIGC artifacts by default.

Recommended sequencing inside PR-10c:

1. add protocol/schema and import-guard scaffolding
2. add participant binding plus trace correlation
3. add dynamic wrapped-tool governance seam
4. add interruption pause/resume bridge
5. add workflow trace/export additive metadata
6. publish the advanced recipe last

---

## Exit Criteria

- `OpenAIAgentsAdapter` is real, optional, and fail-closed.
- The adapter truthfully supports the subset listed above and rejects the rest.
- The host still owns `Runner`, sessions, tool execution, approvals, and
  provider wiring.
- The default `v0.9.0` adopter path remains excellent without Bedrock, A2A, or
  OpenAI Agents SDK integration.
