# AEGIS `v0.9.0` Release Truth and Governance Hardening Development Spec

Date: 2026-05-05
Status: Proposed development spec
Baseline package release: `0.3.3`
Target track: `v0.9.0` source-only beta hardening before PR-11 beta freeze
Document kind: development specification plus implementation plan

---

## Intent

This development spec converts the critical critique into an implementation
sequence.

The first priority is not new capability. The first priority is to make the
release story unambiguous. A governance SDK must tell users exactly what is
published, what is source-only beta, what is local-only, what is supported, and
what is explicitly outside the threat model.

After release truth is aligned, the plan hardens the highest-risk runtime gaps:

- atomic split-token consumption
- audit context data controls
- deeper tool governance
- clearer risk, guard, and postcondition semantics
- adapter compatibility evidence

- [SLSA Build Track v1.2](https://slsa.dev/spec/v1.2/build-track-basics)

Research-driven deltas to fold into the release plan:

- Treat agentic risk as multi-step action risk, not merely bad-output risk.
- Add release provenance, build attestation, dependency, and CI-hardening gates
  before any public beta claim. This checkout has no `.github` workflow files
  observed, so CI/release hardening is a real gap, not paperwork.
- Bind workflow intent, subject, audience, purpose, participant, step, policy
  digest, and allowed-tool digest into session and split-token evidence.
- Treat tool descriptors, agent cards, MCP/A2A metadata, OpenAI Agents SDK
  object inspection, and adapter trace metadata as untrusted runtime supply
  chain inputs.
- Require safer audit-context defaults for prompts, memory-like context,
  retrieved documents, tool arguments, identifiers, and provenance.
- Harden approval checkpoints against human-agent trust exploitation by making
  approval evidence explicit, scoped, time-bound, and reviewable.
- Add emergency disablement, revocation, and incident-response paths for tools,
  adapters, prompts, policies, starter templates, and release artifacts.

### Non-Negotiable Engineering Rules

- All runtime governance failures must fail closed with typed AEGIS errors and
  bounded failure metadata.
- No workstream may add a required provider SDK, cloud credential, network
  service, or hosted runtime dependency to the default adopter path.
- Optional adapters remain public submodules only. They must not be re-exported
  from top-level `aegis` unless a later release explicitly changes that
  contract.
- Schema additions must be additive for existing `0.3.x` policies unless a
  workstream explicitly introduces a beta-only default with migration guidance.
- Root schemas under `schemas/` and packaged schemas under `aegis/schemas/`
  must stay byte-for-byte or semantically synchronized.
- Audit artifacts must remain JSON-serializable and schema-valid on pass and
  fail paths.
- Context controls must never redact the fields required to correlate workflow
  and invocation artifacts unless the selected mode explicitly says correlation
  is unavailable.
- Lint owns deterministic findings. Doctor owns severity and remediation unless
  a separate CLI contract change is accepted.
- Compatibility matrices must name exact refs and versions. Do not replace
  version-specific evidence with general compatibility language.
- Release-facing docs must state exact support status for PyPI, source-only
  beta, local-only, remote branch, and archived docs.

### Runtime Contract Details

Split-token consumption:

- Introduce one module-private helper in `aegis/_internal/enforcement.py`,
  for example `_consume_precall_token_once(...)`.
- The helper owns the lock, registry check, `_consumed` check, registry add,
  and `_consumed=True` mutation.
- Both module-level `enforce_post_call(...)` and `AEGIS.enforce_post_call(...)`
  must call the helper after output type and serializability validation and
  before Phase B policy checks.
- The helper must accept enough context to build the same failure artifact and
  sink behavior that each caller emits today.
- Async wrappers must reach the same helper through the synchronous Phase B
  implementation path or an explicitly shared helper.

Audit context controls:

- Implement context processing in one place close to
  `generate_audit_artifact(...)` so pass and fail artifacts cannot diverge.
- Use path-aware traversal for nested dict/list values.
- Redaction decisions must consider both key names and string values.
- Record `metadata.audit_context_policy.mode`, `classification`,
  `redacted_count`, `hashed_count`, `omitted_count`, and `preserved_paths`.
- If a redaction pattern itself is invalid, policy or constructor validation
  must fail before enforcement begins.

Tool Governance v2:

- Convert allowed-tool policy entries into an internal normalized descriptor
  object before validation.
- Continue accepting existing entries with only `name` and `max_calls`.
- Validate emergency disablement before budget consumption.
- Validate descriptors before trusting adapter- or host-supplied tool metadata.
- Tool result validation is conditional: if result evidence is absent, only
  result rules marked required may fail the invocation.

Approval and revocation:

- Approval evidence must bind to step, participant, purpose, tool,
  destination, data class, side-effect level, policy basis, and expiry when
  those fields are present.
- Revocation checks run before dynamic tool authorization and before budget
  consumption.
- Revocation should support exact ids and digest-based ids so compromised
  descriptors can be disabled even if a name is reused.

### Schema And Artifact Compatibility

- `audit_schema_version` must change only when emitted artifact shape changes in
  a way consumers need to branch on.
- Additive metadata under `metadata.*` is preferred over new top-level audit
  fields unless a top-level field is required for lineage or schema clarity.
- Policy schema additions must include root and packaged schema updates,
  starter policy updates where relevant, and at least one negative schema test.
- Golden replay updates must be deliberate. If an artifact checksum changes
  because metadata changed, document the reason in the PR summary.
- Operator exports may preserve richer metadata than audit exports. Audit
  exports must stay redacted by default.

## Workstream 2 - Claim Tightening and Threat Model

Goal: make marketing language match the code's actual security model.

Required wording change:

- Replace unqualified "tamper-evident audit artifact" with:
  "checksum-based audit artifacts, with optional signing and audit chaining for
  tamper-evidence."

Apply the wording across maintained docs. Archived articles can keep historical
language if they are clearly marked as archived, but release-facing docs must
be precise.

Add a README section near the top:

```markdown
## Threat Model

AEGIS protects against accidental bypass, misconfiguration, missing policy
inputs, invalid roles, invalid schemas, unsupported workflow transitions,
ordinary split-token replay, and host integration mistakes.

AEGIS does not sandbox hostile in-process Python code, contain malicious
dependencies, isolate tenants, protect secrets placed into audit context by the
host, or replace provider/runtime/network security controls.
```

Add an agentic-risk subsection that maps the OWASP Agentic Top 10 to one of
three buckets:

- supported directly in `v0.9.0`
- partially mitigated when hosts provide the required evidence
- outside the SDK threat model

Required bucket decisions:

<!-- markdownlint-disable MD013 -->

| Risk | Required AEGIS stance |
| --- | --- |
| Agent goal hijack | Mitigated only through deterministic policy, intent-bound workflow evidence, and host/tool controls. AEGIS does not make natural-language inputs intrinsically trustworthy. |
| Tool misuse | Current name/count controls are insufficient for mature governance; Tool Governance v2 is the beta hardening target. |
| Identity and privilege abuse | AEGIS validates participant/step evidence supplied by the host; it does not issue credentials or own IAM. |
| Agentic supply chain | AEGIS can pin and validate policy, tool, adapter, and descriptor metadata; it does not make third-party code safe. |
| Unexpected code execution | Explicitly out of scope except for blocking or requiring approval for code-execution tools. AEGIS is not a sandbox. |
| Memory/context poisoning | AEGIS can require provenance and redact/hash audit context; it does not operate a memory quarantine or vector DB security layer. |
| Insecure inter-agent communication | Adapter-boundary validation is in scope; transport security, mTLS, and remote protocol operation are host-owned. |
| Cascading failures | Budgets, sequence checks, circuit-breaker-style failures, and workflow traces are in scope. |
| Human-agent trust exploitation | Approval evidence shape is in scope; human training and organizational approval staffing are out of scope. |
| Rogue agents | Capability manifests, revocation, and quarantine guidance are in scope; autonomous agent containment is host-owned. |

## Workstream 3 - Atomic Split-Token And Intent-Bound Consumption

Goal: close the known check-then-add race in split enforcement and make
workflow/session tokens carry enough immutable intent evidence to detect scope
drift.

Current issue:

- `_consumed_token_registry` is process-local.
- `set.__contains__` and `set.add` are individually protected by the GIL, but
  the replay check and registration are not atomic together.
- Concurrent Phase B calls using a clone of the same `PreCallResult` can both
  pass the registry check before either registers the token.

Implementation plan:

- Add a module-private `threading.Lock`, for example
  `_consumed_token_registry_lock`.
- Centralize token consumption in a private helper so module-level and
  instance-scoped paths cannot drift.
- Preserve current semantics where invalid output does not consume a token.
- Add or verify an immutable token evidence digest that covers:
  - policy checksum or canonical policy digest
  - invocation checksum or canonical Phase A evidence
  - session id, step id, participant id, and workflow id where present
  - declared purpose or intent id where present
  - allowed tool names and descriptor digests where present
  - approval checkpoint id where present
  - token issue time and optional expiration when supported
- After output type and JSON-serializability validation, perform this sequence
  under the lock:
  - check `_token_hmac` in `_consumed_token_registry`
  - check `pre_call_result._consumed`
  - add `_token_hmac` to `_consumed_token_registry`
  - set `_consumed=True`
- Keep the earlier replay check as a fast failure path if useful, but repeat it
  under the lock before consuming.
- Update code comments to say the registry is still process-local but token
  consumption is thread-safe inside the process.

Files likely in scope:

- `aegis/_internal/enforcement.py`
- `tests/` split enforcement tests
- `docs/USAGE.md`
- `docs/PUBLIC_INTEGRATION_CONTRACT.md`

Required tests:

- Same `PreCallResult` consumed twice sequentially: first succeeds, second
  fails.
- Deepcopy or pickle clone consumed after original: fails.
- Two threads racing original and clone: exactly one succeeds.
- Instance API and module-level API both use the same atomic helper.
- Async post-call path inherits the same protection.
- Session token rejects completion if step, participant, workflow, purpose,
  policy digest, or tool descriptor digest changed after Phase A.
- Expired or approval-stale token fails closed when expiration is enabled.

Exit gate:

- The known concurrency warning is replaced by a test-backed statement:
  "Consumption is atomic within one Python process. Cross-process replay
  protection requires host-owned storage or a shared registry."
- Workflow token docs can explain exactly which intent and binding fields are
  frozen at authorization time.

## Workstream 4 - Audit Context Data Controls

Goal: prevent arbitrary secrets, PII, PHI, prompts, retrieved documents, tool
arguments, and business identifiers from being emitted by default in enterprise
audit context.

Current issue:

- Audit context is copied from `invocation["context"]`.
- It is capped by top-level key count, not recursively redacted.
- Failure-message redaction does not protect arbitrary context values.

Additive controls:

- Context allowlist mode.
- Context denylist mode.
- Hash-only context mode.
- Recursive redaction mode.
- Configurable redaction patterns.
- Artifact data-classification metadata.
- Prompt-carrier detection for common fields such as `prompt`, `messages`,
  `instructions`, `system_prompt`, `tool_args`, `retrieved_documents`,
  `memory`, `memory_summary`, `embedding`, and `rag_chunks`.
- Separate normalized provenance fields from raw context so lineage can survive
  redaction.
- Retention guidance for audit artifacts that may carry customer identifiers or
  regulated data.

Recommended policy shape:

```yaml
audit:
  context:
    # Modes: full, redacted_recursive, allowlist, denylist, hash_only, omit
    mode: redacted_recursive
    allowlist: ["tenant_id", "session_id", "provenance.source_ids"]
    denylist: ["prompt", "messages", "retrieved_documents", "tool_args"]
    redaction_patterns:
      secret_like: "(?i)(secret|token|password)"
    classification: confidential
    prompt_carrier_fields:
      - prompt
      - messages
      - retrieved_documents
      - memory
```

Recommended API shape:

```python
AEGIS(
    audit_context_mode="redacted_recursive",
    audit_context_allowlist=[...],
    audit_context_denylist=[...],
    redaction_patterns=[...],
)
```

Compatibility rule:

- Do not silently break existing `0.3.x` artifacts in a patch branch.
- For `v0.9.0` beta starters, prefer allowlist or redacted-recursive context.
- Before `1.0.0`, decide whether full-context emission remains opt-in only.

Required implementation details:

- Redact nested dicts and lists recursively.
- Treat key names and values as redaction inputs.
- Preserve JSON-serializability guarantees.
- Add `metadata.audit_context_policy` with mode, classification, and redaction
  counts.
- In hash-only mode, store deterministic hashes, not raw values. Prefer
  HMAC-SHA256 when the host configures a context hash key.
- Ensure provenance fields needed for lineage are either preserved by allowlist
  or separately normalized into top-level `provenance`.

Required tests:

- Nested API keys, bearer tokens, emails, SSNs, and custom patterns are redacted.
- Arbitrary nested secret keys such as `password`, `prompt`, `messages`, and
  `retrieved_documents` do not appear in emitted context under recommended
  starter settings.
- Memory-like and RAG-like fields are redacted, hashed, or omitted under
  recommended starter settings.
- Allowlist mode emits only named paths.
- Denylist mode removes named paths recursively.
- Hash-only mode emits hashes and no raw values.
- Classification metadata appears in the artifact.
- Schema validation still passes.
- Top-level provenance remains available when raw context is redacted.

Exit gate:

- Enterprise docs can state exactly which context fields are emitted and how to
  configure safer modes.

## Workstream 5 - Tool Governance v2

Goal: evolve tool policy from name/count governance into argument, data,
destination, side-effect, approval, and result governance.

Current issue:

- `tools.allowed_tools` supports only `name` and `max_calls`.
- Runtime validation checks tool allowlist and per-tool counts.

Additive schema target:

```yaml
tools:
  allowed_tools:
    - name: search
      max_calls: 3
      descriptor_checksum: "sha256:..."
      descriptor_source: "policy"
      input_schema:
        type: object
        required: ["query"]
        properties:
          query:
            type: string
      allowed_data_classes: ["public", "internal"]
      side_effect_level: read_only
      requires_approval: false
      allowed_destinations: []
      result_schema:
        type: object
      emergency_disabled: false
```

Required fields and semantics:

<!-- markdownlint-disable MD013 -->

| Field | Semantics |
| --- | --- |
| `name` | Existing allowlist key. |
| `max_calls` | Existing per-invocation or per-session cap. |
| `input_schema` | JSON Schema for tool arguments when provided. |
| `allowed_data_classes` | Allowed sensitivity classes for data sent to the tool. |
| `side_effect_level` | Enum such as `read_only`, `write`, `external_send`, `destructive`. |
| `requires_approval` | Requires recorded approval evidence before execution. |
| `allowed_destinations` | Destination allowlist for network, workspace, tenant, or external send tools. |
| `result_schema` | JSON Schema for tool result metadata when result validation is possible. |
| `descriptor_checksum` | Optional content hash for tool descriptors or adapter-normalized tool metadata. |

| `emergency_disabled` | Hard disable switch for compromised or deprecated tools. |

<!-- markdownlint-enable MD013 -->

Runtime plan:

- Keep existing `name` and `max_calls` behavior backward-compatible.
- Validate `tool_calls[].arguments` against `input_schema` when present.
- Validate `tool_calls[].data_class` against `allowed_data_classes`.
- Validate `tool_calls[].destination` against `allowed_destinations`.
- Validate descriptor checksum/source when descriptor evidence is supplied by an
  adapter or host registry.
- Reject a tool if policy or host revocation metadata marks it disabled.
- Block side-effecting tools without approval when `requires_approval=true`.
- Validate result summaries when the host or adapter supplies result evidence.
- Extend `GovernanceSession.authorize_step_tool_call(...)` to accept bounded

  agent cards, and Bedrock collaborator metadata as untrusted input until

Required tests:

- Existing name/count policies still pass unchanged.
- Unknown tool fails.
- Over-budget tool fails.
- Argument schema mismatch fails.
- Disallowed data class fails.
- Disallowed destination fails.
- Approval-required tool without approval fails.
- Result schema mismatch fails when result evidence is supplied.
- Descriptor checksum mismatch fails when descriptor evidence is required.
- Emergency-disabled tool fails before budget is consumed.
- Adapter dynamic tool authorization uses the same validator.

Exit gate:

- Tool governance docs no longer imply that name/count control is sufficient
  for mature agent governance.

## Workstream 7 - Guard Semantics Hardening

Goal: remove policy-author surprises around dotted identifiers, missing numeric
values, and string membership.

Current behavior to document immediately:

- Dotted identifiers are tokenized, but resolution checks named conditions and
  exact top-level context keys.
- Missing left-side values in numeric comparisons are coerced to `0.0`.
- Membership against a string uses substring semantics.

Hardening plan:

- Fail closed on missing numeric fields by default in the `v0.9.0` beta path.
- Add an explicit compatibility knob only if needed, for example
  `guards.missing_numeric = "zero"`, with default `"error"`.
- Reserve `context.<path>` for nested context resolution.
- Preserve exact-key lookup for bare identifiers so existing policies with
  dotted literal context keys can keep working.
- Document string membership as substring behavior. Consider a later
  `contains()` or `list_contains()` guard function if stricter semantics are
  needed.

Required tests:

- Missing numeric left side raises `GuardEvaluationError`.
- `context.tenant.tier == "enterprise"` resolves nested context paths.
- Bare `tenant.tier` still resolves an exact top-level key named
  `tenant.tier` if present.
- String membership behavior is pinned by tests.
- Unknown boolean lookup remains fail-closed.

Exit gate:

- Policy authors can predict guard behavior without reading the parser source.

## Workstream 11 - Approval, Revocation, and Incident Response Hardening

Goal: address human-agent trust exploitation, rogue-agent, and cascading
failure risks without making AEGIS a hosted runtime or incident-response
platform.

Approval evidence requirements:

<!-- markdownlint-disable MD013 -->

| Field | Required semantics |
| --- | --- |
| `approval_id` | Stable id recorded in workflow and invocation evidence. |
| `requester` | Agent, participant, user, or host component requesting approval. |
| `approver` | Human or system identity that approved or denied. |
| `subject` | Step, action, tool, destination, data class, or policy exception being approved. |
| `policy_basis` | Policy rule, workflow rule, or guard that required approval. |
| `side_effect_level` | `read_only`, `write`, `external_send`, `destructive`, or stricter local enum. |
| `data_class` | Data sensitivity class involved in the approved action. |
| `destination` | External system, tenant, workspace, or endpoint class. |
| `approved_at` | Timestamp. |
| `expires_at` | Required for privileged, external-send, or destructive actions. |
| `rationale` | Bounded text or structured reason, redacted by audit-context policy. |
| `decision` | `approved`, `denied`, `expired`, or `revoked`. |

<!-- markdownlint-enable MD013 -->

Rules:

- Approval evidence must be immutable once recorded.
- Stale approval fails closed.
- An approval for one step, participant, purpose, destination, or tool does not
  authorize another unless policy explicitly allows reuse.
- Destructive, external-send, or privilege-escalating actions require explicit
  side-effect and destination evidence.
- Approval summaries must be auditable without exposing raw prompts,
  retrieved documents, or tool arguments by default.
- Where the host provides identity separation evidence, prevent self-approval
  for high-impact actions. If the host does not provide enough evidence, fail
  closed when policy requires separation of duties.

Revocation and emergency-disable requirements:

- Add a revocation metadata shape for tools, adapters, prompts, starter
  templates, policy checksums, descriptor checksums, and release artifacts.
- Support a host-provided revocation registry or policy section that can disable
  compromised surfaces by id and digest.
- Revocation checks happen before budget consumption and before dynamic tool
  authorization.
- Revocation decisions are recorded in FAIL artifacts with stable reason codes.
- Docs include emergency procedures for:
  - compromised adapter descriptor
  - malicious or vulnerable starter template
  - policy accidentally granting excessive authority
  - audit artifact leaked with sensitive context
  - release artifact or PyPI publishing compromise

Security program updates:

- Update `SECURITY.md` to distinguish supported package releases, source-only
  beta code, optional adapters, and demo assets.
- Add vulnerability triage categories for:
  - enforcement bypass
  - audit omission or integrity failure
  - secret or regulated-data exposure through artifacts
  - adapter boundary bypass
  - release or supply-chain compromise
- Add beta-freeze residual-risk acceptance notes for known non-goals such as
  sandboxing, tenant isolation, hosted IAM, transport security, and malicious
  dependency containment.

Required tests:

- Approval required without evidence fails.
- Approval with mismatched step, participant, destination, data class, or side
  effect fails.
- Expired approval fails.
- Revoked approval fails.
- Emergency-disabled tool or adapter fails before budget consumption.
- Revoked policy or descriptor checksum fails with a stable reason code.
- Failure artifact contains bounded, redacted approval/revocation metadata.

Exit gate:

- Operators have a documented way to pause, revoke, and investigate compromised
  governance surfaces without claiming AEGIS owns orchestration or credentials.
